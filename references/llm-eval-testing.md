# AI 系统评测可信性（R-24）

**一句话主线：demo 看着不错 ≠ 评测通过；跑了一遍单次 ≠ 有回归基线。本规则只回答一件事——你拿到的分数、通过率、judge 结论，能不能支撑「可以上线 / 变更有效」这个决定。**

> 适用：LLM / RAG / Agent / 分类抽取 / 代码生成等 AI 系统的离线评测、模型替换、prompt 变更与放量评审 ｜ 配套：`assets/llm-eval-matrix-template.md` · `scripts/llm-eval-audit.py` ｜ 相关规则：R-9（证据链）、R-22（指标口径，评测也是指标）、R-11（评测数据来源）、`ai-native-testing.md`（AI for QA 与注入手法）

## 0. 触发条件与不适用

| 场景 | 是否触发 | 说明 |
|---|---|---|
| 上线、换模型、改 prompt / 检索 / 工具权限前要给出结论 | ✅ 必做 | 必须有基线、采样与置信区间；不得只交一张 demo 截图 |
| 汇报「提升 X%」「准确率 90%」 | ✅ 必做 | 先交代评测集、n、判定器与分母；不得把单次观察当总体 |
| 引入 LLM-as-judge 自动打分 | ✅ 必做 | judge 必须校准并留人工样本；不得让 generator 给自己打分 |
| 只有可交互 demo、没有标注数据 | ◐ 降级 | 先做 30~50 条分层 smoke，只报「未发现阻断问题」；不得写「评测通过」 |
| 内部原型、无评测预算 | ◐ 降级 | 缩到核心意图 + 安全负例，人工双标 30 条；不得省略失败与超时统计 |
| 纯规则、确定性模块 | ❌ 不适用 | 用单元/契约测试；不得套用 LLM 评测的置信区间话术 |
| 引用厂商跑分、公开榜单 | ❌ 不适用 | 只能当背景；不得当作本项目验收证据 |
| 仅 UI 改动、未触碰模型与数据 | ❌ 不适用 | 走前端/接口回归；不得借评测名义跳过功能测试 |
| 对外宣传材料要引用评测结论 | ✅ 必做 | 附评测集、n、CI 与失败明细；不得只引用最高分 |

## 1. 先问 8 个契约问题

1. 任务是什么：输入、输出、允许的多种正确答案、拒答边界，能否写成一句话？
2. 判定标准谁来定：规则、人工双标，还是 LLM judge？谁对误判负责？
3. 评测集从哪来、多大：真实日志、人工构造、公开基准各占多少？覆盖哪些分层？
4. 是否与训练 / 微调 / few-shot 示例重叠？重叠比例如何检查、由谁复核？
5. 模型与版本是否锁定：写 snapshot 还是家族别名？judge 与 generator 各是什么版本？
6. `temperature` / `top_p` / `seed` / 最大 token 是否固定？服务端路由是否可能换后端？
7. 允许的失败率、成本与延迟预算是多少？p95 超多少算不可接受？
8. 失败的业务后果是什么：答错、拒答、幻觉、越权工具调用、数据外泄，哪类不可接受？

把 8 问答案放在报告首页；任何一问空白，结论只能写「待补证」，不得写「通过」。

## 2. 评测集与污染

- **构成**：按业务意图分层（高频、长尾、否定、多轮、边界），每类 ≥30 条，合计 ≥200 条；不足 200 条只报点估计与样本量，不报「显著」。
- **golden 来源**：优先真实脱敏日志 + 业务专家标注；公开基准只做补充，单列来源，不与自建集混算。
- **版本化**：文件名带 `version`，记录 `sha256`、条数、采集时间、标注人；改一条也要升版本，否则跨版本分数不可比。
- **污染检查**：公开基准题面泄漏、训练集重叠、few-shot 示例混入评测集、时间穿越（用未来数据评测过去模型）。检查结论写「查了什么、怎么查、残留风险」。

| 检查 | 方法 | 通过标准 |
|---|---|---|
| 公开基准泄漏 | 题面 n-gram / 哈希比对 | 重合样本单列，不得混入主指标 |
| 训练集重叠 | 子串命中 + embedding 近邻抽样 | 重叠比例可解释并剔除 |
| 时间穿越 | 核对样本时间戳与模型知识截止 | 评测数据早于截止时间 |

- **退化集与对抗集**：空输入、超长输入、否定改写、错别字、注入串、越权指令；不得只放「正常能答对」的样本。
- **分层权重**：同时报「按业务占比加权」与「等权」两个口径；两者结论冲突时以等权暴露长尾，不得只挑好看的那个汇报。

## 3. 非确定性与采样

- 每个 case 采样 **n ≥ 3（建议 5）**；`temperature=0` 也不保证确定（batch 组合、浮点、服务端路由、版本灰度）。
- 报告写清 **pass@1** 还是 **pass@k**：pass@1 = 单次通过概率；pass@k = k 次里任一次通过。两者不可混比。
- 区间：pass rate 配 **Wilson 95% CI**；小样本配对比较用 **McNemar 精确检验**（只看不一致对 b / c）。
  - Wilson：`(p + z²/2n ± z·√(p(1-p)/n + z²/4n²)) / (1 + z²/n)`，`z = 1.96`。
  - McNemar 精确双尾：`p = min(1, 2·Σ_{i=0..min(b,c)} C(b+c,i) / 2^(b+c))`。
- 「单次跑完就宣称提升 X%」无效：一次采样无法区分模型差异与采样噪声；没有区间就无法判断最小可检测差异。
- 样本量估算：要在 80% 检出 5 个百分点差异，配对样本通常需上百 case；几十条只能发现大退化。

## 4. 判定器可信性（最容易造假的一环）

| 判定方式 | 最低校准 | 可用条件 | 造假信号 |
|---|---|---|---|
| 规则 / 单测断言 | 覆盖正反例 | 断言与业务契约一致，失败可解释 | 只断言 `passed`，不校验内容 |
| 人工双标 | 每类 ≥30 条双人标 | **Cohen's κ ≥ 0.60**；分歧有仲裁 | 一人标完再「补签」第二人 |
| LLM-as-judge | 与人工一致率 **≥ 80%** | judge ≠ generator（不同模型、不同 prompt）；rubric 与 prompt 版本化；A/B 位置交换；控制长度偏见 | 同模型自评、judge prompt 随手改、只看平均分不看分歧 |

judge 上线前必须用人工标注集校准并在报告中给出 κ 或一致率；κ < 0.60 时 judge 结论只能当线索，不得当验收门槛。

判定器结论要能追溯到 rubric 版本与原始样本；只存一个平均分、不存逐条判定，视为不可复核。

## 5. 失败分类与分母

| 类别 | 例子 | 是否计入分母 | 口径 |
|---|---|---|---|
| 能力失败 | 答错、检索错、工具选错 | ✅ | 计为 fail |
| 格式失败 | JSON 解析失败、缺字段 | ✅ | 计为 fail，不重试后抹掉 |
| 拒答 | 该答不答、安全拒答误伤 | ✅ | 单列比例，不混入「通过」 |
| 超时 | 超过 SLA | ✅ | 计为 fail；**超时算通过是造假** |
| 限流 / 服务错误 | 429、5xx | ✅ | 计入分母并单列，不得剔除 |
| 工具错误 | 调用失败、权限拒绝 | ✅ | 计入分母，区分「模型错」与「工具错」 |

分母必须包含失败、超时、限流与拒答；只统计成功调用会把可用率从 70% 粉饰成 95%。示例：100 次调用 20 次超时、10 次答错，只报 `70/80 = 87.5%` 就是造假，正确口径是 `70/100 = 70%`。

## 6. 成本与延迟

- 延迟报 **p50 / p95**（nearest-rank 口径写明），不报平均值冒充尾延迟；流式场景另报首 token 延迟。
- 成本报 token 数与 `$`，区分输入/输出单价、缓存命中与重试消耗；预算超支要判定「停止放量」还是「降级模型」。
- 同一张表里同时给质量、p95、单次成本，避免「分数涨了但成本翻三倍」被隐藏。
- 缓存命中单列；命中率高不等于质量高，不得把缓存节省的成本算成模型能力提升。

## 7. 安全与越权用例（衔接 `ai-native-testing.md`，不重复注入手法）

- **prompt injection（直接 / 间接）**：用户输入与检索文档都可能带指令；判定 = 是否执行了非预期指令、是否泄露系统提示。
- **工具权限最小化**：只读工具不得产生写操作；判定 = 越权调用是否被拒绝并留痕。
- **系统提示与数据外泄**：要求模型复述隐藏提示、其他用户数据；判定 = 拒绝或脱敏。
- **RAG 越权检索**（与 R-4 租户交叉）：构造他租户文档 ID；判定 = 检索层过滤生效，而不是靠模型自觉。
- **输出渲染 XSS**：模型输出被当 HTML/Markdown 渲染；判定 = 转义/白名单生效。
- **PII 回显**：手机号、地址、证件号；判定 = 脱敏或不回显。

每条安全用例都要有「期望 / 实测 / 判定」三列，不能只写「已测试」。越权用例优先用双租户、双角色做否定路径，不得只测允许路径。

## 8. 回归与放量门槛

- 固定基线：上一版模型或默认配置，同评测集、同采样参数、同判定器。
- 指标与阈值：质量（pass rate + CI）、安全（阻断用例 0 容忍）、成本、p95；阈值必须有来源（历史分布或业务 SLA），不得来自单次观察。
- 显著性：配对 case 用 McNemar；显著回归一票否决，显著提升也要看绝对 CI 下界是否过线。
- 放量：5% → 25% → 50% → 100%，每档看真实流量指标与兜底；定义回滚条件（质量跌超阈值、p95 超 SLA、安全告警）。
- 回滚演练：先在 5% 流量模拟一次回滚，确认指标与告警能在约定时间内恢复；不得只写回滚预案不演练。
- **离线绿 ≠ 线上好**：分布漂移、真实 query 长尾、工具/检索线上差异都会让离线结论失效；离线只证明「已知集上没退化」。

## 9. 静态扫描规则 LE-01 ~ LE-10

| 编号 | 反模式 | 为什么错 | 判据（可 grep 识别） |
|---|---|---|---|
| LE-01 | n=1 单次判定 | 无法区分模型差异与采样噪声 | `num_runs/samples/runs = 1`、`range(1)`、`--runs 1` |
| LE-02 | temperature 未固定或设高方差 | 单点分数不可复现 | 调用处无 `temperature`；`temperature >= 0.6` 或 `1.0` |
| LE-03 | 模型版本未 pin | 换版后分数不可比 | 引号内 `gpt-4` / `claude-3` 等别名且无日期/snapshot |
| LE-04 | judge 与 generator 同模型 | 自偏好偏差，评分不可信 | `JUDGE_MODEL = GENERATOR_MODEL` 或两者同字符串 |
| LE-05 | 只报绝对分、无基线 | 不知道好坏与是否回归 | 有 `accuracy/pass_rate/score`，全文无 `baseline/delta/p_value/wilson` |
| LE-06 | 超时/错误排除出分母 | 失败被悄悄消失 | `passed / (total - errors)`、`total = ... - timeout`、`except: pass` |
| LE-07 | 无污染检查 | 训练集重叠会虚高 | 读 `eval_set/benchmark` 且全文无 `contamination/overlap/泄漏/去重` |
| LE-08 | 评测集未版本化 | 结果不可复现、跨版本不可比 | 文件名 `eval/golden/test_set` 且无 `version/hash/collected_at` |
| LE-09 | 阈值来自单次观察 | 门槛本身没有统计依据 | `threshold/min_pass = 0.87` 且无 `CI/sample/baseline/wilson/kappa` |
| LE-10 | 只测 happy path | 真实失败路径未覆盖 | 遍历 `cases/eval_set` 只断言通过，无 `error/timeout/refusal/injection` |

## 10. 验证命令

```bash
# Windows PowerShell 同样可用；路径按项目实际调整
python scripts/llm-eval-audit.py scan .
python scripts/llm-eval-audit.py scan . --include-docs      # 需要看 README/手册时才开
python scripts/llm-eval-audit.py stats --runs runs.jsonl --baseline baseline.jsonl --judge judge.jsonl --fail-on-gap
python scripts/llm-eval-audit.py cases
python scripts/llm-eval-audit.py --self-test
```

**扫描范围契约（v1.14 dogfood 修正）**：`scan` **默认只扫代码与配置**（`.py/.js/.ts/.tsx/.ipynb/.yaml/.yml/.json/.jsonl`），跳过 `.md`——手册、README 与设计文档经常在正文里**引用**反模式原文（「不要写 `temperature: 1.0`」），正则会命中并被当成缺陷，这是噪声而非证据。需要检查文档中的示例时显式加 `--include-docs`，并逐条按「引用 / 实践」裁决后写进报告；不加该参数时**不得**声称「文档已检查」。

**输入契约**：`runs.jsonl` 每行 `{"case_id": str, "run": int, "passed": bool, "model": str, "temperature": number|null, "latency_ms": number, "tokens": number, "cost": number, "error": str|null}`；`judge.jsonl` 每行 `{"case_id": str, "judge_label": str, "human_label": str}`；`baseline.jsonl` 与 `runs.jsonl` 同构。

**输出契约**：总体 pass rate + Wilson 95% CI、逐 case 的 n 与 pass rate、`n<3` 清单、error/timeout 占比（计入分母）、p50/p95、总 token 与 `$`；传 `--baseline` 输出 McNemar 双尾 p 与「显著 / 不显著」；传 `--judge` 输出 po、pe、Cohen's κ 与可用性。

**退出码**：`0` 未触发门槛；`1` `--fail-on-gap` 命中（pass rate 低于 `--min-pass`、κ 低于 `--min-kappa`、存在 n<3、或显著回归）；`2` 参数缺失或输入不可读 / JSON 解析失败。`stats` 默认 `--min-pass 0.80`、`--min-kappa 0.60`。

## 11. 报告证据写法（R-24）

1. 评测任务与输入输出契约（一句话 + 允许的多种答案）。
2. 评测集来源、分层、条数、版本 hash、采集时间与污染检查结论。
3. 采样次数 n、`temperature/top_p/seed`、pass@1 或 pass@k 口径。
4. 判定器类型、人工校准样本、κ 或一致率、judge 与 generator 的模型差异。
5. 总体与逐类 pass rate + Wilson 95% CI，以及失败/超时分母。
6. 基线版本、McNemar p 与「显著 / 不显著」；安全用例逐条判定。
7. p50/p95、token、`$` 成本与预算结论。
8. 放量/回滚条件，以及「离线结论不能覆盖什么」。

证据落在 `reports/` 或测试记忆树，附原始 JSONL 与命令输出；只放截图不算证据链。

**不得**写：「跑通了」≠「评测有效」、「LLM judge 说好」≠「好」、「单次 87 分」≠「87 分」、「prompt 改了分数涨了」≠「模型更好」、「评测集 20 条」≠「有统计结论」、「离线绿」≠「线上可用」。

## 12. 项目形态 → 证据

| 形态 | 必做 | 可降级 |
|---|---|---|
| RAG 问答 | 分层评测集、检索/生成分开判、引用正确性、租户越权 | 超长文档与多轮可先做 smoke |
| Agent 工具调用 | 工具选择/参数/权限、越权拒绝、失败注入、轨迹判定 | 低频工具可抽样 |
| 分类 / 抽取 | 每类 ≥30、混淆矩阵、κ、门槛来源 | 长尾类只报 CI 与样本量 |
| 代码生成 | 编译/单测执行判定、pass@k、安全扫描 | 复杂仓库可缩到核心文件 |
| 纯前端调用第三方 API | 契约、超时/限流、降级文案、成本上限 | 模型质量可引用厂商报告并标注 |
| 无评测预算的原型 | 30~50 条 smoke + 人工双标 + 安全负例 | 不得写「通过」，只能写「未发现阻断」 |
