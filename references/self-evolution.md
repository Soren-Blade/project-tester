# 自我进化协议（本技能的元规范）

> 蒸馏自 `naodeng/awesome-qa-skills` 的 Skill Engineering 横向治理（skill-change-verification / skill-quality-review / skill-evaluation / `SKILL_EVAL_RULES.md` 的本地确定性检测）、`Existing / Enhance / Merge / Match / New` 治理分类，以及本技能原有的三层记忆机制。
> 解决一个原有矛盾：`evolution.md` 规定"技能本体改动需用户批准"，而用户又明确授权「每日自动升级 Skills」。本文件划清两种上下文的边界。

## 1. 两种上下文，两套权限（核心裁决）

| 上下文 | 谁在发起 | 能否改 SKILL.md / references / assets | 依据 |
|---|---|---|---|
| **A. 运行时**：用本技能去测某个项目 | 普通用户会话 | **不能**。只写记忆树、只提 `[技能改进]` 提案，改动由用户决定 | 防止自我漂移、防止测试过程中悄悄改规则 |
| **B. 每日升级**：本自动化任务 | 用户明确授权的定时任务 | **可以**，但必须走完 §3 的门禁并留版本证据 | 用户指令"每日升级 Skills / 自动迭代并全局安装 / 更新 README / 上传 GitHub" |

一句话：**测项目时不自治，升级技能时授权自治**。运行时提案区（`global-lessons.md` 的 `[技能改进]`）是 B 的输入队列。

## 2. 三层记忆（沿用，不变）

```
第 1 层 项目级   <项目>/.test-memory/lessons.md      本项目的坑与回归关注点
第 2 层 跨项目   <技能>/memory/global-lessons.md      通用规律，开局即读
第 3 层 技能本体 SKILL.md / references / assets      流程与手法本身（仅 B 可改）
```

新增第 4 个载体：**`CHANGELOG.md` + 版本号**——记录"为什么改、依据什么来源、怎么验的"，让进化可追溯、可回滚。

## 3. 每日升级的标准流程（B 上下文必须走完）

```
① 读记忆   读 automation memory.md 的历史执行摘要 + CHANGELOG 末条，避免重复升级
② 查新     联网检索权威资料（标准/官方文档/优质仓库），记录来源 URL
③ 蒸馏     把资料压缩成可执行规则/表格/命令，禁止堆砌术语与空话
④ 分类     对每处改动标注治理动作：
            Existing 保留 / Enhance 增强 / Merge 合并 / Match 对齐 / New 新建
            优先 Enhance 已有文件，控制目录膨胀
⑤ 落盘     只改 project-tester/ 内文件；不改其他文件夹
⑥ 自检     python scripts/selfcheck.py（frontmatter、引用完整、版本一致、无占位 URL、行数）
            + 回归：旧示例是否仍成立、五阶段是否仍闭环、记忆树 <100 行纪律是否保留
⑦ 版本     SKILL.md frontmatter version +1；CHANGELOG.md 追加一条（日期/版本/来源/改动/自检结果）
⑧ 同步     cp -r 源 → ~/.agents/skills/project-tester/，diff 校验一致
⑨ 提交     git add / commit（约定 `feat(vN): 每日升级 #M <主题>`）/ push 到 GitHub
⑩ 回写     automation memory.md 写高层摘要；报告交付
```

**门禁（任一失败即停止后续步骤并如实上报）**：自检不通过 → 不升版本、不同步、不提交；同步后 diff 不一致 → 重新同步；push 失败 → 保留本地成果并明确说明未上传。

## 4. 变更证据要求（skill-change-verification 的本地化）

每轮升级在 CHANGELOG 里必须能回答：

| 问题 | 证据形式 |
|---|---|
| 改了什么 | 文件清单 + 治理分类 |
| 依据什么 | 来源名称 + URL + 关键结论（不写"参考了若干资料"） |
| 怎么验证 | `selfcheck.py` 输出 + 回归检查项 |
| 影响什么 | 新增/修改的手册是否改变五阶段流程、是否需要改示例 |
| 能否回滚 | git commit hash |

区分四种结论，不许互相冒充：**静态记录**（文件写了）／**评测准备度**（有自检用例）／**运行时质量**（真实测过项目）／**发布批准**（用户认可）。目录数量增加只证明第一种。

## 5. 蒸馏质量门槛（拒绝"伪升级"）

| ❌ 不合格 | ✅ 合格 |
|---|---|
| 新增文件只是把旧内容换个标题 | 每一条都能直接转成测试动作或判据 |
| "要认真测试""注意安全"类空话 | `[校验] 金额接口必打 0 和 -1 — 应用：…` 式可执行条目 |
| 抄一长段标准原文 | 压成"风险 → 最小测试动作 → 通过判据"三列表 |
| 引入一个跑不起来的重型工具当默认 | 保留零依赖降级路径（`tools.md` 纪律） |
| 只加不删，目录无限膨胀 | Merge 冗余、归档 30 天未用条目 |

**每轮至少留一条可证伪的规则**：写清"在什么情况下这条规则不适用"，比多抄十条标准更有价值。

## 6. global-lessons.md 的维护

- 格式：`[标签] 教训 — 应用：怎么用`；标签：环境 / 工具 / 流程 / 手法 / 安全 / 技能改进
- 条目 > 40 行时修剪：连续两轮没用上的移入文末"归档"或删除
- `[技能改进]` 提案区是下一轮升级的输入；处理后在 CHANGELOG 标注"已吸收 / 已驳回 + 理由"
- 只记**可执行**规律，不记一次性搜索结果与临时路径

## 7. 版本规则

- 语义化 `MAJOR.MINOR.PATCH`：新增能力手册 / 重构流程 → MINOR；修错字与断链 → PATCH；五阶段模型变更 → MAJOR
- 每次升级只升一级，与 CHANGELOG 末条、SKILL.md frontmatter、README 徽章三者一致（由 `selfcheck.py` 校验）
- 每轮对应一个「每日升级 #M」序号，与 git commit message 对齐

## 8. 衡量进化（报告末尾可选一行）

`本轮进化：新增手册 N 份 / 增强 M 份，蒸馏来源 K 个，自检 X 项全通过，新增通用教训 n 条；下次预计省时 ___`。让进化可见，才有无限进步的正反馈——但**省时是估计值，不是承诺**。
