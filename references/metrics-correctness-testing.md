# 指标口径与报表可信（R-22）

一句话：**报表测试不是看「数字能不能显示」，而是看「同一个词在两处是否指同一件事」**——「活跃用户」「支付订单」「GMV」在 dashboard、API、源表 SQL 三处各算一遍，差值要么被归因写清，要么就是缺陷；分母悄悄换了人群，比小数点错一位更常见也更贵。

适用：任何产出指标、看板、报表、导出、增长/营收/留存分析、A/B 实验结论的项目；SQL 直连 BI、dbt/指标语义层、埋点看板、财务对账报表、定时邮件日报都算。
配套：`assets/metrics-correctness-matrix-template.md`（矩阵）、`scripts/metric-audit.py`（`scan` / `check` / `cases` / `--self-test`）。
相关规则：R-22（本手册）；**R-15 金额与账务**（GMV / 实收 / 退款口径必须与账本、渠道对账单一致）；**R-19 查询分页**（`total` 必须与列表同一 `WHERE`，报表总数同理）；**R-17 缓存新鲜度**（看板 TTL 与「最后更新时间」展示）；**R-13 时间时区**（时间窗左闭右开、UTC 与本地展示）；**R-11 测试数据**（测试单/假账号污染指标）；**R-21 搜索指标**（CTR、零结果率的分母是曝光还是会话）。三条交叉：**指标对不上 = 口径 + 时间窗 + 去重键**，三者缺一就无从判定，只能写「待确认」。

## 0. 触发条件与不适用

| 场景 | 是否触发 | 说明 |
|---|---|---|
| 任何 dashboard / 报表 / 定时日报 / 邮件指标 | ✅ 必做 | 主战场：每个被展示的数字都要能追到源表 SQL |
| 增长、营收、留存、漏斗、转化率看板 | ✅ 必做 | 分母漂移与去重是最常见缺陷，**不得**只核对「有没有数」 |
| A/B 实验结论、分群对比、实验平台读数 | ✅ 必做 | 先做 SRM 再谈显著，**不得**跳过分配检查直接报提升 |
| 对外披露 / 财报 / 投资人材料 / 客户 SLA 报表 | ✅ 必做（最高） | 一个点差异都要归因，**不得**以「大致一致」结案 |
| dbt / 语义层 / 指标平台的定义变更（vN→vN+1） | ✅ 必做 | 新老口径并存期双跑对账，**不得**只改文档不验历史可比性 |
| 用户投诉「导出 CSV 与看板不一致」 | ✅ 必做 | 导出与看板必须同源同口径，**不得**只修其中一处 |
| 纯事务系统、无任何指标产出也无看板 | ❌ 不适用 | 只写「不适用：不产出指标与报表」，**不得**写「数据准确 / 报表没问题」 |
| 只有 UI 数字、无源表/仓库/API 访问权限 | ◐ 降级 | 只写「仅核对展示层，未与源表对账」，**不得**写「报表正确 / 指标可信」 |
| 一次性 ad-hoc 查数、不进入任何看板与对外材料 | ◐ 部分 | 只核对 SQL 与口径（分子/分母/时间窗），**不得**写「报表已验收」 |
| 纯前端 mock 数字 demo、无数据管道 | ❌ 不适用 | 只写「不适用：无真实指标链路」，**不得**写「指标已验证」 |

## 1. 指标定义卡（Metric Contract）

一个指标没有定义卡就不具备被对账的资格。十项缺一项，结论上限是「待确认」：

1. **业务问题**：这个数回答谁在什么决策上的什么问题（答不出 = 虚荣指标，不必测）
2. **分子**：精确过滤条件（状态枚举、事件名、金额符号），写成可粘贴的 SQL 谓词
3. **分母**：人群（登录/游客/新老）、时间窗、去重键；比率类没有分母就没有意义
4. **时间窗与时区**：左闭右开 `[start, end)`，写明时区（如 `Asia/Shanghai`）与库内存储时区（多为 UTC）
5. **数据源与表**：库名/schema/表、是否 CDC、埋点 SDK 版本、语义层模型版本
6. **去重键**：`user_id`（用户级）/ `order_id`（订单级）/ `event_id`（事件级），必须显式声明
7. **排除项**：测试单、内部账号、机器人流量、退款单、软删行、重复事件、异常大额单
8. **更新频率与新鲜度**：T+1 还是小时级、SLA（如 `freshness < 6h`）、看板缓存 TTL
9. **负责人**：数据 owner + 业务 owner（对不上时找谁裁决）
10. **版本号**：`metric@vN` + 生效日期 + 与上一版是否可比

**示例定义卡（订单转化率）**：

| 项 | 内容 |
|---|---|
| ① 业务问题 | 本周「访问过商品详情页的用户」中有多少最终「支付成功」，用于判断详情页改版是否提升转化 |
| ② 分子 | 该周内 `orders.status IN ('paid','shipped','completed')` 的支付成功订单，按 `order_id` 去重；退款单不计 |
| ③ 分母 | 同一周 `page_view` 事件中 `page='product_detail'` 的去重 `user_id`；游客以 `device_id` 计入并单列 |
| ④ 时间窗/时区 | `[2026-11-09T00:00:00+08:00, 2026-11-16T00:00:00+08:00)`；库内 UTC 存储，展示 Asia/Shanghai |
| ⑤ 数据源与表 | `dwd.page_view`（埋点）、`dwd.orders`（交易库 CDC），语义模型 `dbt v1.13` |
| ⑥ 去重键 | 分母 `user_id`，分子 `order_id`；口径声明：**用户级**转化率（一人多单计 1 个转化用户），非订单级 |
| ⑦ 排除项 | `is_test=true`、内部账号、`ua` 命中机器人、`refunded_at IS NOT NULL`、`deleted_at IS NOT NULL`、`event_id` 重复 |
| ⑧ 更新频率/新鲜度 | T+1 04:00 产出，`freshness < 6h`；看板缓存 15 分钟 |
| ⑨ 负责人 | 数据 @growth-bi；业务 @growth-pm |
| ⑩ 版本号 | `conversion_rate@v3`，2026-10-01 生效（分母由「全部访问」改为「详情页访问」，历史不可直接比较） |

判据：定义卡缺 ③ 分母、④ 时间窗/时区、⑥ 去重键 任一项 → 该指标不可对账，**不得**给出「通过」；口径变更未写版本与生效日 → 按指标缺陷处理（见 §9），且历史数字须标注「不可直接对比」。

## 2. 对账（reconciliation）

**三处对账**：dashboard 显示值 / API 返回值 / 源表 SQL 直算值。三处必须固定同一时间窗、同一时区、同一去重键，并各自记录**取数时间戳**（缓存与迟到数据会让同一查询在不同时刻给出不同答案）。

**步骤**：① 冻结口径（定义卡）→ ② 三处取数并留原文 → ③ 算绝对差 `|a-b|` 与相对差 `|a-b|/source` → ④ 按归因树逐层排除 → ⑤ 结论写「一致 / 已归因 / 未归因（待确认）」。

**阈值（双条件取严，同时满足才算一致）**：

| 指标类型 | 相对差 | 绝对差 | 判据 |
|---|---|---|---|
| 计数类（订单、用户、事件） | ≤ 0.5% | ≤ 2 单/人 | 两个条件都满足才「一致」；任一超出 → 待确认 |
| 金额类（GMV、实收、退款） | ≤ 0.1% | ≤ 1 元（或 1 个最小币种单位） | 与 R-15 账本/渠道对账单交叉 |
| 比率类（转化率、留存率） | ≤ 0.2 个百分点 | — | 分子与分母两侧都要对，不能只对结果 |
| 去重人数类（DAU/UV） | ≤ 1% | ≤ 50 人 | 采样/HLL 估算须显式声明误差 |

**差异归因树（按顺序排除，不得跳步）**：

1. **口径不同**（分子/分母过滤条件不一致，最常见）→ **数据迟到**（T+1 未跑完或上游分区缺失）：比对两边 `WHERE` 逐行 diff、看分区 `max(ingested_at)` 与行数
2. **去重不同**（`COUNT(*)` vs `COUNT(DISTINCT user_id)`，事件级 vs 订单级）→ **时区**（UTC 与 `+08:00` 跨日，边界日差一天的量，见 R-13）：并排计数、边界日归桶对照
3. **缓存**（看板 TTL 内旧值，比对 `Age`/`last_updated` 与源表最新分区）→ **抽样/估算**（HLL、`approx_count_distinct`、10% 面板）：声明误差并给小样本验证

**单日 vs 区间（可加性）**：计数与金额可加（去重后），**比率与均值不可加**。「日均值不可加」：周一 50/1000=5%、周二 50/100=50%，两日合计 100/1100=9.09%，既不等于两日简单平均 27.5%，也不等于加权前的任何直觉值；同理「日均 DAU × 7 ≠ 周活」。区间报表必须单独用区间窗口算，**不得**把日粒度结果求和/求平均冒充区间值。

**源表 SQL 骨架**：

```sql
-- 分子：支付订单（左闭右开窗口 + 排除项）
SELECT COUNT(DISTINCT o.order_id) AS paid_orders
FROM dwd.orders o LEFT JOIN dim.users u ON u.user_id = o.user_id
WHERE o.status IN ('paid','shipped','completed')
  AND o.paid_at >= :start AND o.paid_at < :end      -- 勿用 BETWEEN（含右端）
  AND COALESCE(o.is_test, false) = false AND o.refunded_at IS NULL
  AND COALESCE(u.is_internal, false) = false AND COALESCE(o.deleted_at, 'infinity') > :end;

-- 转化率：分子必须是分母子集（同一 user_id 集合）
WITH denom AS (SELECT DISTINCT user_id FROM dwd.page_view
               WHERE event_name = 'page_view' AND page = 'product_detail'
                 AND event_time >= :start AND event_time < :end AND user_id IS NOT NULL),
     numer AS (SELECT DISTINCT user_id FROM dwd.orders
               WHERE status IN ('paid','shipped','completed')
                 AND paid_at >= :start AND paid_at < :end AND refunded_at IS NULL)
SELECT (SELECT COUNT(*) FROM numer WHERE user_id IN (SELECT user_id FROM denom))::numeric
       / NULLIF((SELECT COUNT(*) FROM denom), 0) AS conversion_rate;
```

## 3. 七个口径陷阱（现象 → 识别方法 → 证据）

| # | 陷阱 | 现象 | 识别方法 | 证据 |
|---|---|---|---|---|
| 1 | **分母漂移** | 注册口径从「全部注册」改为「完成邮箱验证」，转化率一夜上涨而业务没变 | 拉两版定义卡 diff；同窗口按新旧分母双算 | 两版分母人数 + 比率差异，注明生效日与是否可比 |
| 2 | **去重** | 同一订单多次支付回调 → 订单数虚高；`COUNT(*)` 无 DISTINCT | 对源表做 `COUNT(*)` vs `COUNT(DISTINCT order_id)` 对照；查回调表 `event_id` 重复数 | 两值 + 重复 `event_id` 样本 + 去重键声明 |
| 3 | **时区/跨日边界** | UTC 存、`+08:00` 展示，23:30 的订单落到「昨天」或「今天」不一致 | 取 23:30–00:30 的订单，分别按 UTC 日与本地日归桶 | 同一订单在两套时区下的归属日期 + 两边日汇总差 |
| 4 | **迟到数据与 backfill** | 事件延迟 T+1 到达，昨日数字今日变大；重跑任务翻倍 | 对比 T+0/T+1/T+7 三次快照；查 backfill 是否分区覆盖还是 append | 三次快照值 + restatement 幅度 + 任务写入模式 |
| 5 | **测试/内部/机器人流量** | 测试单、压测账号、爬虫 UA 进入 GMV/DAU | 按 `is_test`、内部 ID 白名单、UA/IP 频次分布切分 | 排除前后指标差 + 被排除样本样例（脱敏） |
| 6 | **退款与负向金额** | GMV 含退款、部分退款未冲减、退款单被算成负订单 | 定义卡写清 GMV 是「下单口径 / 支付口径 / 净收口径」；对退款单独计数 | 三口径并排数值 + 部分退款样例（1 单退 2 件中 1 件） |
| 7 | **幸存者偏差与辛普森悖论** | 汇总转化率上升，但每个渠道都在下降（人群结构变化） | 按渠道/设备/新老拆层，逐层与汇总对照 | 分层表（层内比率 + 层权重）+ 汇总值，指出方向反转的那一层 |

判据：七项里至少逐项写出「命中 / 未命中 + 证据」；**不得**用「口径应该没问题」代替证据，也**不得**只写「已确认口径一致」而不给两侧 SQL。

## 4. A/B 与分群：先看样本再谈显著

- **SRM（sample ratio mismatch）**：先验分配比例 vs 实际进入人数，卡方检验 `χ² = Σ (O−E)² / E`，A/B 两臂 `df = 1`；`p < 0.001` 视为**分配异常**，实验结论直接作废，回查分流哈希、埋点丢失、重定向、机器人过滤、时区截断。
- **固定样本量 / 固定时长**：实验前用 power 分析定 `n`（`α=0.05`、`power=0.8`、最小可检测效应 MDE），到量或到期再读；**不得**边跑边看 p 值（peeking 把实际 α 抬到 20%~30%，「跑到达标就停」等于自欺）。
- **多重比较**：同时看 `m` 个指标/分层时，Bonferroni 用 `α/m`，或 Holm 逐步校正；**不得**从 20 个指标里挑一个 `p<0.05` 报「显著提升」。
- **分子必须是分母的子集**：转化率分子用户必须 ⊂ 分母用户；出现 >100%、负数、分母为 0 时按 MA-07 判缺陷。

**数值例子（SRM）**：对照组 5000 访问 / 250 转化，实验组 5100 访问 / 280 转化。

- 分配：总 10100，期望各 5050；`χ² = (5000−5050)²/5050 + (5100−5050)²/5050 ≈ 0.99`，`df=1`，`p ≈ 0.32` → **无 SRM**，可以继续看效果。
- 转化：5.00% vs 5.49%；期望转化各 265，`χ² = (250−265)²/265 + (280−265)²/265 ≈ 1.70`，`p ≈ 0.19` → 不显著。**不得**写「提升 0.49 个百分点，效果显著」；正确写法是「点估计 +0.49pp，`p≈0.19`，未达显著，需延长或扩量」。脚本会给出 `χ²` 与 `p`；手算与脚本不一致时以脚本为准并核对自由度与是否用了 Yates 校正。

## 5. 数据新鲜度与重述

- **事件延迟分布**：给出 p50 / p95 延迟（如 p50=2 分钟、p95=47 分钟），以及「T+1 04:00 时点已到齐比例」（如 99.2%）——只写「准实时」不算证据。
- **T+1 重述（restatement）幅度**：同一业务日 T+0 与 T+1 的值差，如「昨日 GMV 在 T+1 增长 1.8%，主因 2.3% 的事件延迟到达」，并说明可接受上限。
- **缓存 TTL 与「最后更新时间」**：看板必须展示 `last_updated` 与数据截止分区；无时间戳的看板按 MA-06 判缺陷。缓存 TTL 内数字不变属预期，**不得**把缓存旧值当成「数据错了」或把新值当「已核对」。
- **dashboard 与源表时间差 / backfill 幂等**：记录 `dashboard_last_updated` 与 `source_max_partition_time` 的差，超过 SLA（如 6h）即「数据停更」，先报停更再谈数字；重跑同一分区必须**覆盖**而非 append，证据是重跑后行数/金额不变（`Σ` 与 `COUNT(DISTINCT)` 前后相等），否则一次回刷就把指标翻倍。

## 6. 可加性与聚合

| 运算 | 可加性 | 典型错误 | 正确做法 |
|---|---|---|---|
| `COUNT` / `SUM` | 可加（按唯一键去重后） | 各地区 UV 相加 ≠ 全国 UV（同一人跨区重复） | 全局按 `user_id` 去重，或声明「地区人数之和」口径 |
| `AVG` / 比率 | **不可加** | 各组转化率求平均 = 「平均的平均」 | 用总分子/总分母重算（加权） |
| 分位数 | **不可加** | 每日 p95 求平均 ≠ 区间 p95 | 保留原始分布或 t-digest/HLL 草图，区间重算 |
| 留存 / 漏斗 | 分母是**队列** | 把不同注册周的留存率平均 | 按注册周分队列，结论写队列口径与观察窗口 |
| 时间序列 | 需对齐 | 周起始（周一 vs 周日）、财政月 vs 自然月、ISO 周跨年 | 声明并固定日历（如 `week_start=Monday`、`fiscal_year_start`） |

判据：任何「合计」必须能指出是**先聚合再相加**还是**先相加再算比率**；写错方向即 MA-02。**不得**把「平均的平均」「分位数平均」写进结论。

## 7. 数据质量门禁

- **dbt tests / Great Expectations / Soda**：`unique`（主键唯一）、`not_null`、`accepted_values`（状态枚举）、`relationships`（外键不悬空）为最低集，指标模型关键列必须有测试、失败即阻断；跨源与业务规则断言（「支付金额 > 0」「订单数日环比在 ±30% 内」）用 GE/Soda，结果落表并带运行时间。
- **结构异常清单（每条给阈值）**：行数突变 > ±30%（需排除大促/月末结算）；空值率 > 1%（关键列 > 0）；主键重复 > 0；枚举越界 > 0；金额为负（退款表除外）；未来时间戳 `> now() + 5min`；分区缺失。
- **指标级断言**：「昨日 GMV 环比 −30%」告警必须能区分**业务真变化**与**管道断流**——同时看上游分区是否为空、事件延迟 p95 是否飙升、行数是否骤降；只报「GMV 跌了」而不给这三项，等于没告警。
- 判据：门禁必须能**阻断**（`--fail` 退出码非 0 或任务红灯），只发通知不阻断按「无门禁」计。

## 8. 权限与合规

- **行级权限**：租户/区域过滤必须在查询层（`WHERE tenant_id = :ctx`），取回后在应用层过滤会让导出与看板看到不该看的数据（与 R-4、R-19 的 `total` 同源要求一致）。
- **小样本重识别**：聚合结果样本 < `k`（如 `k=10`）时必须抑制或合并桶，**不得**在按地区/部门/年龄的细分里展示个位数人数；「1 个人 = 100% 转化率」本身就是泄漏。
- **导出、分享与 PII**：公开看板链接、CSV 导出、订阅邮件都要过同一权限，**不得**因为「只是导出」而绕过行级过滤；手机号/邮箱/身份证列不进指标明细，只进脱敏维度，导出文件默认不带 PII。

## 9. 反模式与缺陷判定

| 编号 | 现象 | 级别 | 判据 |
|---|---|---|---|
| MA-01 | `COUNT(*)` 未过滤状态/软删（含取消、删除、草稿单） | HIGH（对外披露 S1） | 指标值与定义卡口径对照，差值可归因到被多算的行 |
| MA-02 | 平均的平均 / 各组比率求平均 | HIGH | 与总分子/总分母重算值比对，差异 > 0.5pp |
| MA-03 | 日期无时区或 `BETWEEN start AND end` 含右端 | HIGH | 边界日重复/缺失行数 + `[start,end)` 改写后对照 |
| MA-04 | 缺 `DISTINCT`/去重键，重复事件被计数 | HIGH | `COUNT(*)` vs `COUNT(DISTINCT key)` 差值 + 重复样本 |
| MA-05 | 金额 `SUM` 用 float / double | MEDIUM | 累加结果与账本差 > 0.01，且随行数增长（见 R-15） |
| MA-06 | 看板无「最后更新时间」/数据截止时间 | MEDIUM | 页面与 API 均无时间戳，无法判断是否停更 |
| MA-07 | 转化率分子/分母过滤条件不一致（分子有用户不在分母） | HIGH | 比率 > 100% 或分子集合差集 > 0 |
| MA-08 | 缺测试单/内部账号/机器人过滤 | HIGH | 排除前后指标差 > 0.5%，且能列出被混入样本 |
| MA-09 | 先 `SELECT *` 拉全表再在应用层过滤/聚合 | MEDIUM | 查询日志行数与返回行数差一个量级；口径散落在代码 |
| MA-10 | 无 SRM 检查 / 偷看 p 值 / 无多重比较校正 | HIGH | 实际分配比偏离期望且 `p<0.001`，或结论来自中途停止 |

## 10. 验证命令（零依赖优先）

```bash
# 1) 静态扫描指标代码与 SQL（口径硬编码、无时区、BETWEEN、无 DISTINCT）
python scripts/metric-audit.py scan <path> --format markdown
# 2) 对账清单：三处取值、陷阱、SRM、新鲜度
python scripts/metric-audit.py check --file metrics.json --format markdown
python scripts/metric-audit.py check --file metrics.json --format markdown --fail-on-gap
# 3) 反例集与自检
python scripts/metric-audit.py cases
python scripts/metric-audit.py --self-test
```

**输入 JSON 契约**（字段名固定，缺字段按缺口计）：

```json
{"metrics":[{"name":"paid_orders","numerator":"status='paid'","denominator":"created_at in [start,end)","dashboard":1234,"source":1301,"tolerance_pct":0.5,"timezone":"Asia/Shanghai","dedupe_key":"order_id","freshness_minutes":90}],"srm":[{"experiment":"exp-1","control":{"visitors":5000,"conversions":250},"treatment":{"visitors":5100,"conversions":280}}]}
```

`--fail-on-gap` 的触发条件（任一命中即退出码非 0）：① 任一 metric 相对差 `> tolerance_pct`；② 任一实验 SRM `p < 0.001`；③ 定义卡缺 `numerator` / `denominator` / `timezone` / `dedupe_key` 任一。报告里要抄命令原文 + 退出码 + 输出行，**不得**只写「脚本通过」。

## 11. 报告证据写法（R-22 七项）

1. **定义卡原文**：分子/分母/时间窗与时区/去重键/排除项/负责人/版本号（缺项要标注）；
2. **三处对账数值**：dashboard、API、源表 SQL 三值与相对差/绝对差，附各自取数时间戳与 SQL 原文；
3. **口径陷阱逐项处置**：七个陷阱逐条「命中 / 未命中 + 证据」，命中项给修复前后对照；
4. **新鲜度时间戳**：`last_updated`、数据截止分区、事件延迟 p50/p95、重述幅度；
5. **SRM 卡方与 p**：每臂人数、期望人数、`χ²`、`df`、`p`，以及是否触发回查；
6. **样本量**：实验设计 `n`、MDE、实际到量、是否中途读值、多重比较校正方式；
7. **看板截图 / 查询结果原文**：截图要带时间与筛选条件，SQL 结果要带列名与行数。

**不得**写：「数据准确」「报表没问题」「指标正常」「转化率提升」「口径应该一致」「对账大致通过」「看板显示和大盘差不多」「实验显著（未给 SRM 与 p）」。**不得**把「三处数字都能看到」冒充「三处一致」，**不得**把「脚本扫描无命中」冒充「口径正确」，**不得**把「单日对得上」冒充「区间可加」。

## 12. 项目形态 → 证据

| 形态 | 必做 | 证据 |
|---|---|---|
| SaaS 增长看板 | DAU/MAU、留存队列、转化率定义卡 + 三处对账 | 定义卡 + 三值表 + 留存队列窗口声明 |
| 电商 GMV/转化 | GMV 三口径（下单/支付/净收）、退款冲减、去重回调 | 三口径并排 + 退款样本 + `order_id` 去重前后数量 |
| 金融对账 | 报表与账本/渠道对账单逐笔或分层核对 | 差异笔数、方向、金额分布 + 归因（见 R-15） |
| 内部 BI 自助取数 | 语义层指标定义唯一性、同一问题不同人不同答案 | 同一指标两套 SQL 的 diff + 统一后对照 |
