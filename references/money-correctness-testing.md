# 金额与账务正确性测试（R-15）

> 一句话：金额测试不是「看看数字对不对」，而是**用最小单位整数 + 币种 exponent + 显式舍入 + 复式账本**四把尺子，把「显示价 / 应付额 / 实扣额 / 入账额 / 可退额」逐层对齐；任何一层对不上，就是钱算错了。
> 适用：电商、订阅计费、钱包、支付/退款、发票、分账、优惠券、积分兑换、加密货币以外的任何「钱」。
> 配套：`assets/money-matrix-template.md`、`scripts/money-audit.py`、`references/api-testing.md`（契约）、`references/data-integrity-testing.md`（超卖/重复扣款）、`references/privacy-compliance-testing.md`（卡号与 PII）。
> 相关规则：R-15 本手册；R-1 链路（支付链路端到端）、R-11 测试数据（金额夹具）、R-12 身份与会话（越权退款）、R-13 时间（账期/时区切日）、R-14 备份恢复（账本恢复后仍平衡）。

## 0. 触发条件与不适用

| 触发条件（命中任一即必须做 R-15） | 不适用写法（必须写清理由） |
|---|---|
| 代码/接口里出现 `amount`、`price`、`total`、`balance`、`refund`、`invoice` | 纯展示型静态页，无交易、无金额输入 → 「不适用：无交易金额」 |
| 接入了支付渠道（Stripe/支付宝/微信/Adyen 等） | 内部积分且**明确不可兑换现金**、无账本 → 「不适用：非货币积分」 |
| 有优惠、税、运费、分账、退款、订阅续费 | 只做汇率展示、不做结算 → 「不适用：仅展示汇率，无资金流」 |
| 有多币种或跨境 | 单币种且 exponent 与代码常量一致，仍须测 M-05/M-06 → 不得整体标不适用 |
| 有对账/财务报表/结算单 | — |

> 判定口径：只要「用户可能被扣钱」或「账上可能记错」，就**不得**以「金额很简单」为由跳过 R-15。

## 1. 先记住的事实（可直接当期望值）

### 1.1 浮点不是钱

- `0.1 + 0.2 === 0.30000000000000004`（IEEE 754 binary64）。任何「先转 float 再相加再比较」的金额代码都不可信。
- JS `(2.675).toFixed(2)` 得到 `"2.67"`：toFixed 对二进制近似值做舍入，不是对十进制 2.675 做四舍五入。Python `round(2.675, 2)` 同样是 `2.67`，且 `round(0.5) == 0`（银行家舍入）。
- 推论：**期望值必须用十进制字符串/整数最小单位表达**；用 `0.1+0.2` 当断言基准的测试本身是错的。

### 1.2 币种 exponent（ISO 4217，写进测试数据）

| exponent | 币种（示例） | 最小单位含义 |
|---|---|---|
| 0 | JPY、KRW、VND、CLP、ISK、PYG、UGX、XAF、XOF、XPF、KMF、DJF、GNF、BIF、RWF、VUV | 1000 = 1000 元，不是 10.00 |
| 2 | CNY、USD、EUR、GBP、HKD、SGD、AUD、CAD… | 1000 = 10.00 |
| 3 | BHD、JOD、KWD、OMR、TND、IQD、LYD | 1000 = 1.000 |
| 4 | CLF、UYW（ISO 4217 存在 4 位） | 10000 = 1.0000 |

- 支付渠道还有**特殊规则**（以渠道文档为准，实测口径必须进契约）：Stripe 对 ISK、UGX 这类「历史上按两位表示」的零小数币种仍收两位最小单位（5 ISK 传 `amount=500`）；HUF、TWD 仅在 payout 场景视为零小数且金额须被 100 整除；其余零小数币种直接传该币种金额（500 JPY ⇒ `amount=500`，**不要 ×100**）。
- 代码里出现 `* 100` / `/ 100` / `toFixed(2)` / `round(x, 2)` 且没有按币种分支，直接记为**可疑缺陷**（`money-audit.py scan` 的 MO-03/MO-09）。

### 1.3 舍入必须写进契约

四种常见模式，结果不同，**没有「默认正确」**：

| 模式 | 2.5 → 0 位 | 用途 |
|---|---|---|
| half-up（四舍五入） | 3 | 常见发票/零售展示 |
| half-even（银行家舍入） | 2 | 金融统计、部分渠道费率 |
| half-down（五舍六入） | 2 | 少数计费场景 |
| 截断（toward zero） | 2 | 明确「不多收」的场景 |

必须问清并实测：**舍入发生在哪一层**（单价？行小计？订单总额？税额？退款？），以及**展示价与结算价是否用同一模式**。典型缺陷：列表页 `toFixed(2)` 显示 2.68，结算用浮点得到 2.67，用户看到的价格和扣款差 1 分。

税务口径的例子（HMRC VAT）：税额 0.004p 舍为 0，0.005p 进为 0.01（half-up，按 transaction / invoice 计）；若实现是「逐行舍入再汇总」，发票总额会与税局口径差几分——这属于契约问题，**不得**写成「四舍五入都对」。

### 1.4 分摊必须守恒

`100.00 / 3 = 33.333…`。直接 `round(33.333, 2)` 三份得 99.99，丢 1 分。正确做法是**最大余额法**（largest remainder）：

1. 每份先取整到最小单位（floor）；
2. 把剩余的最小单位数按小数部分从大到小分给前 N 份；
3. 断言 `Σ分摊 == 原额`。

同一算法必须用于：优惠券分摊、运费分摊、部分退款、多行订单拆账、分账（split payment）。**未守恒即 S1**（用户可见的丢分/多收）。参照实现：moneyphp `Money::EUR(1000)->allocate([1, 1, 1])` 得 334 / 333 / 333（合计仍 1000）；dinero.js 用不可变的 `amount + currency` 对象表达金额。

### 1.5 复式记账不变量

- 每笔交易：`Σ借方 == Σ贷方`（按币种分别成立）。
- 分录**只追加**，改错用**冲正分录**，不 UPDATE 历史。
- 余额：`期末 = 期初 + 收入 − 支出/退款`，按账户、按币种。
- 跨币种：换汇要两条腿（卖出币种 + 买入币种），汇率与手续费各有科目，不得直接改余额。

## 2. 六面测试法

### 面 1：计价（pricing）

测「同样输入是否得到契约规定的同一结果」，不测 UI：

- 单价 × 数量（含小数单价 19.99×3）；
- 折扣顺序：先打折后减满减 vs 先满减后打折（结果不同，契约必须写死一种）；
- 税：价内税反算（`税 = 含税价 × r/(1+r)`）与价外税（`税 = 不含税价 × r`），价+税必须等于含税价（±0 最小单位）；
- **税额口径**：按行算税再汇总 vs 按订单汇总再算税，结果会差 1 分。例：3 行各 0.335、税率 10%，按订单 `0.335×3×0.1=0.1005→0.10`，按行 `round(0.0335)=0.03×3=0.09`。契约必须写死一种并给出该口径下的期望值；凭「四舍五入都对」判 PASS 无效；
- 运费、包装费、服务费是否参与折扣/计税；
- 会员价/阶梯价/秒杀价与优惠券叠加规则；
- 优惠券门槛按「折前」还是「折后」金额判断。

### 面 2：舍入（rounding）

- 边界值：0.005、0.015、0.025、2.675、1.005（浮点陷阱集中区）；
- 零小数币种（JPY）与三位小数币种（KWD）各跑一单完整链路；
- **展示 vs 结算 vs 退款**三处金额一致性；
- 汇率换算后舍入：先换后舍 vs 先舍后换，差异要写进契约；
- 手续费计算（渠道费率 0.6% + 固定费）的舍入方向。

### 面 3：分摊（allocation）

- 100.00 分 3 份；99.99 分 7 份；0.01 分 3 份（退化场景）；
- 部分退款按行退 vs 按比例退，剩余可退金额精确；
- 多币种订单的优惠分摊；
- 分账（平台/商户/服务商）三方金额之和 == 用户支付额。

### 面 4：账务（ledger）

见 §4 三步法。核心是**订单库、支付流水、账本、渠道对账单**四份数据能逐笔对上。

### 面 5：并发（concurrency）

- 同一订单两次支付回调（渠道重试天然造成）→ 只入账一次；
- 库存 1 件 10 并发 → 成功 ≤1，不超卖；
- 同一优惠券并发核销 → 只成功一次；
- 退款并发 → 累计退款 ≤ 实付（用数据库约束/行锁/幂等键，不靠应用层先查后写）；
- 余额扣减用原子操作（`UPDATE ... SET balance = balance - ? WHERE balance >= ?`），不用读-改-写。

### 面 6：状态机（state machine）

- 订单：待支付 → 已支付 → 已发货 → 已完成；退款/取消/拒付的分支；
- 非法迁移必须被拒（已退款再退款、未支付发货）；
- 部分退款后状态（部分退款/已退款）与可退余额；
- 渠道异步事件与本地状态机的对账（回调丢失时靠主动查询补）。

### 面 7：落盘往返（persistence round-trip，v1.10 dogfood 新增）

内存里算得对，不等于重启后还在。金额系统最低要求「写进去 = 读回来」：

- 下单/支付/退款后 **kill 进程再启动**，订单、支付流水、账本、用户余额仍在且数值一致；
- 进程内缓存的去重键、计数、余额不得是唯一副本；`data.json`/DB 有记录但启动不加载 = S1（写入成功、重启归零）；
- 写入采用「先落盘再返回成功」还是「异步刷盘」要写清丢失窗口；双写（DB + 文件/缓存）要测中途崩溃后两侧是否一致；
- 重启后重放同一 `Idempotency-Key` / `event_id` 仍只生效一次（去重表也必须持久化）；
- 备份/迁移后的金额比对见 `backup-recovery-testing.md` R-14，两边都要有。

## 3. 金额边界清单（每条都要有实测）

| 类别 | 输入 | 期望 |
|---|---|---|
| 零与负 | 0、-0.01、-100 | 0 元订单按契约（拒绝或免支付）；负数一律 4xx 拒绝 |
| 一分钱 | 0.01、最小单位 1 | 可支付/可退；渠道最低金额限制要单独测 |
| 超大 | 1e9、`999999999999`、超过 `BIGINT` | 4xx 拒绝或明确上限，不溢出、不静默截断 |
| 精度 | 0.001（2 位币种）、0.0001 | 拒绝或按契约舍入，不得静默截断 |
| 格式 | 千分位 `1,000.00`、全角 `１００`、科学计数 `1e3` | 明确接受/拒绝；解析失败 4xx 不 500 |
| 币种 | 小写 `cny`、未知 `XXX`、空 | 归一化或拒绝；不得默认 USD |
| 混币种 | 购物车同时含 USD 与 CNY 行、合计直接相加 | 4xx 拒绝（或按声明汇率换算并留痕与舍入证据），不得把 1010 USD 当合法总额（`money-audit.py` LG-06） |
| 数量/客单价 | `qty=-2`、`qty=1.5`、客户端 `unitPrice=0.01`（目录 99.99） | 非正整数拒绝；单价必须服务端按 SKU 重算，客户端金额忽略或 422 |
| 客户端篡改 | body 里 `amount=0.01` 买 100 元商品 | 服务端按 SKU 重算，忽略客户端金额（`money-audit.py` MO-08） |
| 重复提交 | 同 Idempotency-Key 两次 | 同结果、只扣一次 |
| 退款超额 | 退 100.01（实付 100.00） | 拒绝并留痕 |

## 4. 账本对账三步法

**第一步：清单自洽（本地可做，无需渠道）**

用 `python scripts/money-audit.py ledger --file ledger.json` 检查：每笔借贷平衡（LG-02）、无单边分录（LG-03）、小数位不超币种 exponent（LG-04）、无负数金额（LG-05）、不混币（LG-06）。这一步只能证明「清单内部自洽」。

**第二步：订单 ↔ 支付流水**

按 `order_id` / `payment_intent_id` 关联，逐笔比对：应付额 == 渠道实扣额 == 入账额；手续费单独科目；时间戳落在同一账期。

**第三步：账本 ↔ 渠道对账单**

下载渠道结算文件（Stripe Balance Transactions / 支付宝对账单），按交易号逐笔匹配；差异分类为：渠道有本地无（漏单）、本地有渠道无（虚单）、金额差（舍入/手续费/汇率）、状态差（成功/退款/拒付）。**差异率与差异明细必须进报告**，不能用抽样代替。

> 只做到第一步时，报告只能写「账本内部平衡」，**不得**写「对账通过」「账务正确」。

## 5. 缺陷判定与严重级

| 现象 | 级别 | 判据 |
|---|---|---|
| 展示价 ≠ 实扣价（哪怕 1 分） | S1 | 用户可感知的价格欺诈/客诉 |
| 分摊丢分/多收 | S1 | Σ分摊 ≠ 原额，可复现 |
| 重复扣款 / 重复入账 | S1 | 同一订单多次扣款或账本重复 |
| 超卖 / 负库存 | S1 | 库存与订单不一致 |
| 超额退款 | S1 | 累计退款 > 实付 |
| 账本不平 | S1 | 借贷差 ≠ 0 |
| 币种 exponent 写死 2 位 | S2 | 仅影响 0/3 位币种，但属确定性错误 |
| 舍入模式与契约不一致 | S2 | 差 1 最小单位且可复现 |
| 金额错误信息泄露内部细节 | S3 | 仅日志/文案问题 |

> 判 bug 时**必须给出差额的最小单位数**（例：差 1 分 = 1 cent），不接受「看起来不对」。

## 6. 工具：scripts/money-audit.py（零依赖）

```bash
python scripts/money-audit.py scan src/                 # 扫 MO-01~MO-09 金额反模式
python scripts/money-audit.py scan src/ --fail-on-gap   # 有 HIGH 命中则退出码 1
python scripts/money-audit.py ledger --file ledger.json # 对账清单自洽（LG-00~LG-06）
python scripts/money-audit.py cases                     # 取 0.1+0.2 / 2.675 / JPY / KWD / 分摊反例
python scripts/money-audit.py --self-test               # 自检脚本本身
```

- `scan` 只报「可疑写法」，命中要人工确认；**未命中不证明金额正确**。
- `ledger` 只证明给定 JSON 内部自洽；**不证明真实账本完整**。
- 脚本**不联网、不代填**任何字段；结论必须由实测证据支撑。

## 7. 证据与报告写法

- 每条金额结论附：请求/响应原文（含币种与最小单位）、DB 查询结果、账本分录、渠道流水号。
- 金额一律写成「最小单位 + 币种」：`5997 USD cents`、`1000 JPY`、`1234 KWD fils`，避免「59.97 元」这种歧义。
- 报告证据矩阵里 R-15 行写 `PASS / 待确认 / 不适用`，并在证据列给文件路径 + 行号或截图名。
- 没有渠道对账单时，R-15 只能写「部分覆盖」，并在盲区表写清原因。
