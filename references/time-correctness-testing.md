# 时间与时区正确性测试（R-13）

> **一句话**：同一时刻在不同时区、不同的夏令时状态、不同的时钟读数下，系统必须给出同一个正确答案。
> 把时间当「普通字符串」或「普通整数」处理的项目，几乎必然在跨时区、跨 DST、跨年边界上出错。
>
> 适用：任何存储 / 计算 / 展示时间、有定时任务、有过期或 TTL、按时间排序或过滤、有跨时区用户的项目。
> 本手册配套：`assets/time-matrix-template.md`（记录矩阵）、`scripts/time-audit.py`（静态扫描 + DST 计算）。
> 相关规则：**R-13**；与 R-6（数据生命周期/保留期）、R-11（测试数据可复现）、R-14（备份时间点）交叉。

| 有多时区用户、用户可设时区 | 读 §1、§5、§6 |
| 有时间范围查询、报表、排序、分页 | 读 §6、§7 |
| 无任何时间语义（纯算法库、离线转换器） | 报告写「不适用：无时间维度，未做时间正确性验证」，**不得**写「时间处理正确」 |
| 本机无 tzdata 且无法安装 | 写 `BLOCKED: 无 tzdata`，用 Node `Intl` 或 CI 容器拿到证据后再判；**不得**凭「没跑出问题」判 Pass |

## 1. 先问三个问题：存什么、算什么、显示什么

| 层 | 正确口径 | 反模式 | 怎么验证（最小动作） |
|---|---|---|---|
| 存储 | 绝对时刻存 UTC（或带时区的时间类型），并保存产生时刻的**偏移/时区标识** | naive 本地时间入库；字符串无偏移；用 `datetime.now()` 直接落库 | 查 DDL/表结构与一条真实记录：`created_at` 是否带偏移或存 epoch；同一条记录换读时区后是否仍是同一时刻 |
| 计算 | 「时刻」用 epoch/Instant；「日历日」用日历库加**天**，不用 +86400 秒 | `now + 86400` 当明天；`expire = created + 30*24*3600` 当 30 天 | 在 DST 转换日对同一逻辑跑一次：结果与「日历日 +1」是否一致 |
| 显示 | 显式指定时区（用户 profile 或请求参数），格式带偏移 | 依赖服务器默认时区；`toLocaleString()` 不传 `timeZone` | 同一记录用 `TZ=UTC` 与 `TZ=Asia/Shanghai` 各渲染一次，比较是否为同一时刻的不同表示 |

> 核心判据：**改观看时区不应改数据，改数据时区不应改排序。**

## 2. 十类时间缺陷模式（T-01 ~ T-10）

编号与 `scripts/time-audit.py scan` 一致；每条都能落成一次运行时验证。

| 编号 | 缺陷模式 | 最小动作 | 通过判据 |
|---|---|---|---|
| T-01 | 无参 `new Date()` / 隐式读墙上时钟 | 注入可控 clock（`sinon` / Playwright `page.clock` / 依赖注入），跑同一用例两次 | 两次结果一致，且断言不随执行时刻漂移；无注入点时至少记录「无法注入」为盲区 |
| T-02 | JS 把 `'YYYY-MM-DD'` 按 UTC 解析（`new Date('2026-03-08')`） | 在 `TZ=Asia/Shanghai` 下 `new Date('2026-03-08').toISOString()` | 输出不是 `2026-03-08T00:00:00.000Z`（若业务要「本地 3 月 8 日」，必须按本地构造） |
| T-03 | Python naive `datetime.now()/today()` | 在 `TZ=America/New_York` 的 fold 时段（2026-11-01 01:30 本地）生成时间戳 | 两个 fold 实例产生**不同**的可区分值（带 fold/offset），否则同一本地时间会塌成一个时刻 |
| T-04 | `datetime.utcnow()` 返回 naive UTC | 序列化后检查字符串是否带 `Z`/`+00:00` | 带偏移标记；消费端按 UTC 解析后与源时刻相等 |
| T-05 | 固定 86400 秒当一天 | DST 转换日跑「明天」逻辑 | 结果落在日历次日（本地 00:00 或同一钟点），不是 23:00/01:00 |
| T-06 | `toLocale*` 未指定 `timeZone` | 同一时刻在 `TZ=UTC` 与 `TZ=Asia/Shanghai` 渲染 | 输出差异可解释；若产品要求固定时区，输出不随环境漂移 |
| T-07 | 时间用字符串 / 裸时间戳直接比较 | 混合偏移（`+08:00` 与 `Z`）的两条记录排序 | 排序结果按**时刻**正确，而非按字典序 |
| T-08 | DB 列类型无时区语义（PG `timestamp`、MySQL `DATETIME`） | 写入一条带偏移时刻，换 session 时区读回 | 读回仍是同一时刻；或明确记录「按约定存 UTC」并在读写处转换 |
| T-09 | Java `LocalDateTime.now()` / 无时区 API | 跨时区构造事件，检查提醒时刻 | 用 `Instant`/`ZonedDateTime` 时提醒在绝对时刻正确；用 `LocalDateTime` 时能指出错位 |
| T-10 | `SimpleDateFormat` 默认 JVM 时区、非线程安全 | 两个线程并发 format 不同时刻 | 输出互不污染，且时区显式 `setTimeZone` |

补充（不依赖静态扫描，但必测）：

- **精度混用**：秒 / 毫秒 / 微秒混用（`exp * 1000` 漏乘或乘两次）——用 1 秒/1 毫秒边界各测一次。
- **时区缩写歧义**：`CST` 可指中国、美国中部、古巴——API 不得只返回缩写，必须带偏移。
- **历史 DST**：中国 1986–1991 实行过夏令时；用历史日期回归「当天 02:30」任务与出生日期计算。
- **闰日与月末**：2028-02-29、1 月 31 日 +1 月、12 月 31 日跨年；判据是「不崩溃且落到下一个合法日期」。
- **周起始**：ISO 周一 vs 美式周日；按周聚合的报表必须写明口径。

### 2.1 两个非静态扫描项（同样是必测）

- **T-11 tzdata 漂移**：应用容器、DB 容器、JVM、浏览器各带一份时区数据，版本不同会让同一未来时刻解析出不同偏移。不是理论风险：IANA **2026f**（2026-10-27）直接取消了古巴 2026-11-01 的回拨。测法：应用侧与 DB 侧各打印 `python -c "import tzdata;print(tzdata.__version__)"`（或镜像 digest）+ 对 3 个未来时刻（如 2026-12-01、2027-01-01、2027-11-08）打印 offset；**版本或 offset 不一致 → 阻塞发布**，不得写「已知差异」蒙混。
- **T-12 时区配置面**：`TZ` 环境变量、PG `TimeZone`、MySQL `time_zone`、JVM `-Duser.timezone`、cron `CRON_TZ`、容器基础镜像 tzdata。逐项打印实际值做成「配置面 × 实际值」表；所有面必须显式设定，不依赖默认值。

## 3. DST 实测（本手册的强制项）

### 3.1 先拿到该时区该年的 gap / fold

```bash
# 零依赖，读取本机 tzdata；不可用会明确报错，不会伪造结果
python scripts/time-audit.py dst --zone America/New_York --year 2026 --at 02:30
python scripts/time-audit.py dst --zone Europe/Berlin --year 2026 --format json
```

输出给出：转换的 UTC 时刻、前后偏移、`gap`（本地时间不存在）或 `fold`（本地时间出现两次）的本地窗口。

### 3.2 2026 代表时区夹具（已用 `time-audit.py` 实测）

| 时区 | 转换 UTC 时刻 | 类型 | 本地窗口 | 对「每日 02:30」的影响 |
|---|---|---|---|---|
| America/New_York | 2026-03-08T07:00Z | gap | 03-08 02:00–03:00 | 02:30 **不存在**，必须跳过或顺延 |
| America/New_York | 2026-11-01T06:00Z | fold | 11-01 01:00–02:00 | 02:30 在 fold 之外，正常执行一次 |
| Europe/Berlin | 2026-03-29T01:00Z | gap | 03-29 02:00–03:00 | 02:30 **不存在** |
| Europe/Berlin | 2026-10-25T01:00Z | fold | 10-25 02:00–03:00 | 02:30 **出现两次**，必须去重 |
| Australia/Sydney | 2026-04-04T16:00Z | fold | 04-05 02:00–03:00 | 02:30 **出现两次** |
| Australia/Sydney | 2026-10-03T16:00Z | gap | 10-04 02:00–03:00 | 02:30 **不存在** |
| America/Santiago | 2026-04-05T03:00Z | fold | 04-04 23:00–04-05 00:00 | 00:30 **出现两次** |
| America/Santiago | 2026-09-06T04:00Z | gap | 09-06 00:00–01:00 | 00:30 **不存在** |
| Asia/Shanghai | 无 | — | — | 1991 年后无 DST；历史日期另测 |

> 上表是「tzdata 2026.6（对应 IANA 2026f 一系）」的实算结果。tzdb 规则会变（2026f 就取消了古巴 2026-11-01 的回拨），升级依赖或换基础镜像后必须重跑；报告里注明 tzdata/镜像版本。

### 3.3 调度器 DST 行为实测（必须给出执行次数，而不是「任务还在」）

已知事实（只写有原文的）：**cronie 的 `crontab(5)` 明确写：缺失的本地时刻「never match … will not be run」（gap 不跑），重复的本地时刻「will cause matching jobs to be run twice」（fold 跑两次）。** systemd timer / Quartz 的行为本轮未取到原文，**只能实测，不得按「应该」写结论**。

1. 把被测服务/脚本的时区固定为 `TZ=America/New_York`（Node/Python 都认 `TZ`；Windows 下用 Node 的 `Intl` 或容器）。
2. 注册每日 `02:30` 任务，把「当前时刻」注入到转换日前 5 分钟（可控 clock 或短周期触发）。
3. 观察并记录：**是否执行、执行几次、下一次计划时刻是什么、日志时间戳带什么偏移**。
4. 判据：
   - gap 日：**不得静默消失**——不跑要有日志/告警，或顺延到 03:00 后执行一次；前后端归一规则必须一致；
   - fold 日：先记录实际跑了几次（cron 语义就是两次）。若两次，必须有**幂等键（业务键 + 执行窗口，而非原始本地字符串）**保证副作用只发生一次，且日志能区分 first/second（带偏移或 epoch）；重复扣款/重复通知 = S1；
   - 两种情况下「下一次执行时刻」都必须落在未来的合法本地时间。
5. 证据：任务执行计数 + 每次执行的时间戳原文（含偏移）+ 业务副作用条数（如订单/通知表行数）。

> 实现差异必须实测后写：Vixie/cronie cron 的 gap/fold 语义已如上述；systemd timer 的 `OnCalendar` 按本地墙钟计算但 DST 行为未证实（Debian BTS #1033548 只算间接证据）；Quartz 的 `CronTrigger` 有 misfire 策略与 `PreserveHourOfDayAcrossDaylightSavings` / `SkipDayIfHourDoesNotExist` 一类属性，是否生效需实跑；自研 `setInterval(24h)` 会整体漂移 1 小时（推论）。

## 4. 过期、TTL 与宽限期（off-by-one 高发区）

- **三值边界**：`ttl-1s` 有效、`ttl` 临界、`ttl+1s` 失效。临界点写清用的是 `<` 还是 `<=`，两种都测一次。
- **时钟来源**：签发端与校验端是否同一时钟源；允许的 skew（如 60s）是声明值还是隐式值。
- **单位**：秒 vs 毫秒 vs 纳秒；`exp` 是 epoch 秒还是 `Date` 对象。
- **宽限期**：令牌过期后是否仍可用于刷新（refresh grace）、宽限期内是否只允许一次。
- **缓存 TTL 与业务过期**：缓存过期 ≠ 业务过期；两者不一致时以谁为准。
- **判据**：边界两侧的响应码/响应体/数据库状态三者一致；同一请求重复发送在临界点不产生双写。

## 5. 时钟：墙上时钟不可信，单调时钟才可信

| 场景 | 危险写法 | 测法 | 判据 |
|---|---|---|---|
| 超时/耗时 | `end - start` 用墙上时钟 | 测试中回拨系统时钟（容器内 `libfaketime`）或注入时钟跳变 | 超时不因回拨变负/变无限；耗时用 monotonic |
| 限流窗口 | 固定窗口按 `now / 60` | 窗口边界前后各发一次 | 边界处不出现「一分钟内放行两倍」或「跨窗口永久封禁」 |
| 幂等窗口 | 用 `created_at` 字符串比较 | 两条相差 1 秒但跨 DST 的记录 | 仍按时刻判断，不按字典序 |
| 事件排序 | 客户端时间排序 | 客户端时间被回拨/伪造 | 服务端用序号或服务端时间兜底，客户端时间只作展示 |
| 数据库主键 | 时间戳当 ID | 同一毫秒并发插入 | 无冲突或用序列/UUID |

> 不能改系统时钟时，至少把「时钟依赖」注入化并写单元测试；报告里把「未做时钟回拨实测」列为盲区，不得写「时钟安全」。

## 6. 序列化、解析与排序

- **格式**：对外一律 RFC 3339 / ISO 8601 且**带偏移**（`Z` 或 `+08:00`）。只发 `2026-03-08 02:30:00` 的接口必须明确「这是哪个时区」，否则按缺陷记。
- **解析**：无偏移字符串不得默认按服务器时区解析；显式声明时区或缺省拒绝（4xx）二选一，写进契约。
- **排序/比较**：先解析为带偏移时刻再比较；混合偏移的字符串排序必然错。
- **往返**：`parse(format(t)) == t`，对 fold 时段分别用 `fold=0` / `fold=1` 各测一次。
- **展示**：12/24 小时制、AM/PM、locale 数字格式；解析用户输入时不要用浏览器 locale 猜测格式。
- **`-00:00` 语义**：RFC 3339 里它表示「UTC 已知、但本地偏移未知」，不要当成 `+00:00` 用于本地展示；双时区输入（`2026-03-29T02:30:00+08:00[Europe/Berlin]`）应拒绝或按契约取其一。
- **解析歧义**：`10:11:12`、`01/02/03`、`24:00:00`、`2026-02-30`、全角数字都要有明确结果；MySQL 宽松格式会把 `'10:11:12'` 解析成 `2010-11-12`（官方文档明示的坑），这类「静默猜测」一律判缺陷。
- **日志**：日志时间戳统一 UTC 或统一带偏移，且与 trace 时间轴一致；混用会让 R-1 链路排查失真。

## 7. 数据库与查询边界

| 引擎 | 语义要点 | 必测 |
|---|---|---|
| PostgreSQL | `timestamptz` 存 UTC 瞬时（**不保留原始时区**），显示随 session `TimeZone`；`timestamp` 会**静默丢弃**输入时区，且 PG 不做字面量类型推断，`TIMESTAMP '2026-03-29 02:30:00 Europe/Berlin'` 会被当成 without time zone | 同一行在 `SET TIME ZONE 'UTC'` / `'Asia/Shanghai'` 下读回是否同一时刻；`WHERE ts >= '2026-03-08'` 的隐式转换依赖 session 时区；`+ interval '1 day'` 与 `+ interval '24 hours'` 在 DST 日结果不同（day 可能是 23/25 小时），日历语义应测后者 |
| MySQL | `TIMESTAMP` 按会话 `time_zone` ↔ UTC 双向转换、范围到 2038-01-19 03:14:07 UTC；`DATETIME` 不转换、范围 1000–9999；非法日期按 `sql_mode` 变零值 | 写入后改 `time_zone` 读回；插入 `2038-01-19 03:14:08` 应被拒且报错可读；`CAST(col AT TIME ZONE INTERVAL '+00:00' AS DATETIME)` 取 UTC 视图 |
| SQLite | 无原生时间类型，TEXT/INTEGER/REAL 混存会毁掉比较与排序；`now` 是 UTC，`Z` 是 no-op，`±HH:MM` 会被减成 UTC；官方明说「假定每天 86400 秒」 | 全表统一一种口径（建议 TEXT 带 `Z` 或整数 epoch）；`SELECT datetime('now'), datetime('now','localtime')` 验证；混存视为缺陷 |
| 迁移 | 旧列可能按本地时间写入 | 迁移脚本对旧数据的时区假设写明并抽样验证；`up`/`down` 后时刻不变 |

边界查询用例：跨年（12-31 → 01-01）、闰日、DST gap 当天的「全天」范围、时区偏移变更的历史日期。

## 8. 工具与降级

| 工具 | 用途 | 备注 |
|---|---|---|
| `scripts/time-audit.py scan <path>` | 静态扫 T-01~T-10 反模式 | 命中只是可疑；未命中不证明正确；`--fail-on-gap` 用于门禁 |
| `scripts/time-audit.py dst --zone --year [--at]` | 算 gap/fold、判断每日时刻 | 依赖 tzdata；不可用明确报错并给安装提示 |
| Node `Intl.DateTimeFormat` + `TZ` | 无依赖验证时区渲染/DST | `node -e` 一行即可；ICU 需完整 |
| Python `zoneinfo` | 同上 | 无 tzdata 时 `pip install tzdata` |
| `freezegun` / `time-machine` | Python 可控时钟 | 只影响 Python 进程 |
| `libfaketime` | 进程级时钟偏移 | 需要预加载，适合容器 |
| Playwright `page.clock` | 浏览器内假时钟：`setFixedTime` / `install({time})` / `pauseAt` / `fastForward('02:00')` / `runFor`；覆盖 `Date`、`setTimeout/Interval`、`performance`、`Event.timeStamp` | `install` 必须在任何 clock 相关调用之前；与真实网络/服务端时间隔离 |
| `python -c "import tzdata;print(tzdata.__version__)"` | 打印应用侧时区数据版本 | 与 DB/镜像对照，版本不一致即 tzdata 漂移风险 |
| `@sinonjs/fake-timers` | JS 假时钟 | 需检查被测代码是否用它认识的计时器 |
| `zdump -v <zone>` / `date -d` | 系统级查看转换 | Linux/macOS；Windows 用 Node/Python |

降级原则：没有可控时钟时，用**固定输入的纯函数**测试（把 `now` 作为参数传入）优先于改系统时钟；两者都做不到，就只写「未做时钟控制验证」。

## 9. R-13 证据要求（报告矩阵必须能填）

声称「时间处理正确 / 跨时区可用 / DST 安全 / 令牌按时过期」时，至少附：

1. 存储口径证据：DDL 或表结构 + 一条真实记录（含偏移/epoch），说明存的是 UTC 还是本地；
2. 显示口径证据：同一时刻在 ≥2 个时区下的渲染输出；
3. DST 证据：`time-audit.py dst` 输出（含 tzdata 版本）+ 应用侧与 DB 侧 tzdata 版本/3 个未来时刻 offset 对照 + 转换日任务执行次数与时间戳原文；
4. TTL 证据：`ttl-1 / ttl / ttl+1` 三值响应码与状态；
5. 排序/边界证据：混合偏移排序、跨年/闰日各一条；
6. 时钟证据：可控时钟注入的用例，或明确写「未做时钟回拨验证」；
7. 配置面证据：`TZ` / DB `TimeZone` / JVM `user.timezone` / `CRON_TZ` 的实际值表。

只有第 1、2 项：判「部分覆盖，R-13 降级为待确认」；缺 DST 实测不得写「DST 安全」；缺 tzdb 版本不得写「跨时区已验证」。

## 10. 常见误判与禁止写法

- 「服务器是 UTC，所以没问题」——错：用户时区、DST、显示格式、调度器都不在服务器时区里。
- 「用了 moment/dayjs/luxon 就没问题」——错：插件是否加载、tz 数据版本、调用是否传 zone 都要看。
- 「测试环境没复现」——错：需要主动构造 gap/fold，不是等它发生。
- 「时间戳能解析」——不等于「时刻正确」；解析成功只证明格式合法。
- 禁止写：「已支持所有时区」「DST 无影响」「时间处理正确」——除非第 9 节证据齐备。
- 不适用写法：「不适用：无时间维度，未做时间正确性验证」。
