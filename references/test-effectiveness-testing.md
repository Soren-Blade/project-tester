# 测试有效性度量（阶段 3 · 横向叠加）

> 蒸馏自 DORA（部署频率/前置时间/变更失败率/恢复时长）、Google SRE 与 Google 测试博客（flaky 测试）、变异测试工程实践、Martin Fowler《Eradicating Non-Determinism in Tests》；v1.4 追加 GitHub `naodeng/awesome-qa-skills` 的 `automation-roi-analysis` / `test-maintenance-cost-analysis` / `regression-optimization` / `ci-test-optimization` 分类，合并为 §5A 测试经济性/ROI。`CHANGELOG.md` v1.3.0 / v1.4.0 记录逐条来源。
> 定位：前面所有手册都在「**怎么把测试写得更狠**」；本手册回答「**你这一堆测试到底有没有用、值不值**」。高覆盖率 + 一堆 flaky + 低变异得分 = 自我安慰；只报自动化率不报成本 = 另一种自我安慰。度量是给质量结论定量的尺。

## 0. 适用边界与分工

| 触发 | 叠加本手册 | 不适用 |
|---|---|---|
| 项目有 CI、有测试套件、有发布流程，需要量化「测试值不值」 | 是 | 纯手工验证、无任何自动化测试 → 只写「无测试度量基础」 |
| 出现 flaky / 覆盖率虚高 / 发布后频繁回滚 | 强烈建议 | — |
| 只关心单条用例怎么写 | 去 `references/test-design.md` / `quality-gates.md` §5 | 本手册不重复用例设计 |

**三条认知打底**：
1. **覆盖率高 ≠ 测试有效**：代码跑过了但没断言，照样 95%；变异测试专门治这个。
2. **flaky 不是「概率问题」是「纪律问题」**：重试掩盖 ≠ 修复；Google 经验是约 1–2% 的测试会 flaky，放任会让真实回归更晚被发现。
3. **「绿了」的发布仍可能翻车**：变更失败率（CFR）与缺陷逃逸率才是「测试有没有拦住真问题」的真相指标。

## 1. DORA 四指标（发布健康度）

| 指标 | 定义（分子/分母/口径） | Elite 门槛 |
|---|---|---|
| 部署频率（Deployment Frequency） | 单位时间部署次数 | 按需（每天多次） |
| 变更前置时间（Lead Time for Changes） | 提交 → 生产运行的时长 | < 1 小时 |
| **变更失败率（Change Failure Rate, CFR）** | **失败部署数 / 总部署数**（失败=导致服务降级/需回滚/热修的部署） | 0–15% |
| 恢复时长（Mean Time to Recovery, MTTR） | 故障发生 → 恢复服务的时长 | < 1 小时 |

> 度量口径必须写清：**失败部署怎么定义、统计时间窗、数据源（CI/监控）**。CFR 只看「部署是否失败」，不是「用例是否绿」——这正是测试有效性的外部证据。

## 2. 缺陷逃逸率（Defect Escape Rate）

```
缺陷逃逸率 = 生产环境发现的缺陷数 / (生产环境发现数 + 发布前发现数)
```

- 口径：时间窗、缺陷严重度范围（是否含 S3 文案）、缺陷来源（工单/监控/客诉）。
- 判据：逃逸率持续走高 = 测试门禁没拦住该类问题，需回看 `test-design.md` 的覆盖准则。
- 与 CFR 互补：CFR 看「部署坏没坏」，逃逸率看「坏的有没有在出门前被抓」。

## 3. Flaky 测试配额与隔离（重试 ≠ 修复）

flaky = 代码没变、同一测试时过时不过。治理顺序（详见 `quality-gates.md` §4，这里给量化口径）：

| 动作 | 量化 |
|---|---|
| 确认 | 同一用例连续跑 ≥10 次记录通过率；换机器/顺序再跑 |
| 配额 | 全量套件 flaky 比例应远低于 Google 经验的 ~1–2%；超阈值即告警 |
| 隔离 | 修不好就 `quarantine`，带负责人与解除日期；禁止无限重试或静默删除 |
| 反模式 | CI 加 `retries: 3` 宣称「稳定」= 把不确定性藏起来，真实回归更晚暴露 |

**非确定性根因（Martin Fowler）**：时钟/时间、随机数、外部依赖、共享状态、异步等待。修复对应：注入时钟、固定随机种子、mock 外部依赖、自清理共享状态、显式等待条件。

## 4. 变异得分（Mutation Score）

```
变异得分 = 被杀死的变异体数 / 变异体总数
```

| 工具（按栈，缺则注明） | 命令 |
|---|---|
| JS/TS | `npx stryker run` |
| Python | `pip install mutmut && mutmut run` |
| Java | `mvn org.pitest:pitest-maven:mutationCoverage` |
| Rust | `cargo mutants` |

- 判据：核心模块变异得分明显偏低 → 报告写「**覆盖率虚高、测试杀伤力不足**」，补强断言而非堆覆盖率数字。
- AI 生成测试尤其要查：只断言 `is not None`/`toBeTruthy()`、断言「调用过 mock」却不断言业务结果、把实现复制一遍当预期。

## 5. 测试有效性度量卡（E-1 ~ E-10）

| # | 度量/动作 | 口径与判据 |
|---|---|---|
| E-1 | 覆盖率 vs 变异得分对照 | 覆盖率 ≥80% 但变异得分 <60% → 标注「假测试」风险 |
| E-2 | flaky 比例 | 全量套件 flaky 率；超 ~2% 告警 |
| E-3 | 变更失败率 CFR | 失败部署/总部署；Elite <15% |
| E-4 | 缺陷逃逸率 | 生产缺陷/(生产+发布前)；走高即预警 |
| E-5 | 部署频率 / 前置时间 | 反映交付节奏与门禁顺畅度 |
| E-6 | MTTR | 故障恢复时长；反映回滚/可观测能力 |
| E-7 | 重试掩盖检测 | CI 中 `retries` 配置 + quarantine 名单审查 |
| E-8 | 断言强度抽检 | 核心模块断言是否含业务结果而非存在性 |
| E-9 | 选测完整性 | change-to-regression：改模块用例 + P0 全量回归，避免只跑单行改动 |
| E-10 | 套件时长 | 全套 < 15 分钟（超则并行/选测），否则门禁形同虚设 |

## 5A. 测试经济性 / ROI（v1.4 新增，落地顺延提案）

> 蒸馏自 GitHub `naodeng/awesome-qa-skills` 的 `automation-roi-analysis` / `test-maintenance-cost-analysis` / `regression-optimization` / `ci-test-optimization` 技能分类，以及本手册已有的 DORA / 逃逸率 / 套件时长口径。**合并进本手册而非另起新文件**——「测试有没有用」（§1~§5）与「测试值不值」（本节）是同一把尺的两面。

| 类别 | 具体项 | 可取证来源 |
|---|---|---|
| 建设成本 | 写用例、搭框架、接入 CI、造 fixture 的人时 | 迭代记录 / PR / 工时 |
| 运行成本 | CI 分钟数、并发 runner、真机与设备云账单、许可证 | CI 账单 / 平台报表 |
| 维护成本 | 随需求变更改用例、flaky 定位、quarantine 清欠、快照更新 | quarantine 名单 / 提交历史 |
| 反馈时间收益 | 缺陷从引入到被发现的时间缩短、开发者等待时长下降 | CI 时长趋势 / 缺陷时间戳 |
| 逃逸避免成本 | 生产缺陷数 × 平均修复成本（含回滚、客诉、SLA） | 工单 / 监控 / 发布记录 |
| 优化收益 | 选测、并行、缓存、分层后套件时长下降 × 发布频次 | CI 时长前后对照 |

**口径（必须写清，不许只报一个百分数）**：

```
ROI（时间窗 T） = (反馈时间收益 + 逃逸避免成本 + 优化收益 − 建设/运行/维护成本) / (建设/运行/维护成本)
回收周期 = 累计成本回正所需的时间窗
```

- 每个分项写**分子 / 分母 / 数据源 / 时间窗 / 是否估计值**；估计值必须标注「估计」，不得写成实测账单。
- 与 §1~§5 的有效性指标联动：**「套件变快」若伴随变异得分下降或逃逸率上升，是负收益**，不能只报时长下降。
- ROI 是**投入决策依据**，不直接阻断单次发布；但套件时长失控（E-10）或维护成本失控会侵蚀门禁有效性，应回写 `references/quality-gates.md` §6 的 CI 门禁。

**度量卡（E-11 ~ E-14，接在 §5 之后）**：

| # | 度量/动作 | 口径与判据 |
|---|---|---|
| E-11 | 三类成本齐全 | 建设/运行/维护都填数或显式「数据不可得」，不得只算其中一类 |
| E-12 | 收益与有效性联动 | 报时长收益时同列变异得分与逃逸率变化，防止「删用例换速度」 |
| E-13 | 估计值标注 | 每个估计分项标注「估计」与依据；缺账单时写「成本为估计值」 |
| E-14 | 决策闭环 | 结论落到「继续投入 / 缩减某层 / 优化选测 / 停止自动化」之一，附理由 |

> 反模式：只报「自动化率 85%」不报成本；把覆盖率当收益；为凑 ROI 删掉慢但高杀伤力的 E2E；把一次估算当长期结论。

## 5B. AI 生成测试用例的有效性度量（v1.5 新增）

> 蒸馏自本技能 `references/ai-native-testing.md` §3「AI 生成测试的审查纪律」与 `references/quality-gates.md` §5 变异测试口径，并对照 GitHub `naodeng/awesome-qa-skills` 的 `ai-generated-test-review` / `test-effectiveness-analysis` 分类。**合并进本手册**：弱断言审查清单不二次抄写，这里只补「怎么量化」。**未采用**任何声称「AI 提效 X%」的二手数据——缺实测就写「数据不可得」。

| 指标 | 分子 / 分母 / 口径 | 判据 |
|---|---|---|
| 入库率 | 经人工审查后**保留进套件**的用例数 / AI 生成总用例数 | 低不等于差（可能宁缺毋滥），但必须报告，不能只报「生成了 200 条」 |
| 断言强度合格率 | 断言可观测业务结果的用例数 / 入库用例数 | 只断言 `is not None` / `toBeTruthy()` / 「mock 被调用过」的一律不合格；清单见 `references/ai-native-testing.md` §3 |
| 变异杀伤贡献 | 仅由 AI 生成用例杀死的变异体数 / 被杀死变异体总数 | 分母写清变异工具与范围；低贡献＝用例在凑数 |
| 假通过率 | 故意改坏代码后仍为绿的 AI 生成用例数 / 入库用例数 | 最硬的一条：直接证伪「生成即有效」 |
| 审查与维护成本 | 人工 diff 审查 + 后续随需求改用例的人时 | 与 §5A 的建设/维护成本合并，别把「生成快」当净收益 |
| 逃逸拦截贡献 | 生产缺陷中被 AI 生成用例提前捕获的条数 / 生产缺陷总条数 | 口径同 §2；无数据写「数据不可得」，**不填 0** |

**纪律（与 `references/ai-native-testing.md` §3 同源，不重复展开）**：

1. **「跑绿」不是有效性证据**。healer / 自愈的目标是让测试变绿，它可以通过放宽断言、跳过用例、把期望改成实际值来达成；任何 AI 改过的断言都要人工 diff 复核。
2. **分母必须是「入库用例」而非「生成条数」**，并写清时间窗、模型/工具版本、审查人与变异工具。
3. **区分四类结论**（`references/self-evolution.md` §4）：生成了用例只证明「静态记录」；门禁自检绿只证明「评测准备度」；变异杀伤与假通过率实测才谈「运行时质量」；「发布批准」不能由用例数量推出。
4. 审查记录（生成提示词、diff、判定、批准人）登记进 `scripts/evidence-audit.py` 的 manifest，否则 R-9 判证据链缺口。

**度量卡（E-15 ~ E-18）**：

| # | 度量/动作 | 口径与判据 |
|---|---|---|
| E-15 | 入库率与审查记录 | 生成数、入库数、剔除理由三类齐全，不缺审查人 |
| E-16 | 断言强度抽检 | 逐条判「可观测业务结果」还是存在性/实现细节；不合格即打回 |
| E-17 | 假通过率实测 | 故意改坏 ≥1 处核心逻辑，AI 生成用例应转红；全绿即判假通过 |
| E-18 | 变异杀伤与成本联动 | 报「生成快」时同列变异杀伤贡献与审查人时，防止用数量换速度 |

> 反模式：把「AI 生成了 200 条用例」当收益；把 `retries` 后的绿当通过；用 AI 自愈改断言而不留 diff；没有变异工具就把「覆盖率上升」写成「有效性提升」。

## 6. 度量纪律（别用数字美化结论）

- 每个指标写清**分子/分母/数据源/时间窗/解释边界**（同 `quality-gates.md` §7）。
- 缺失证据标 `BLOCKED`/`待确认`，**不填 0 分假装测过**。
- 区分四种结论，不许互相冒充：**静态记录**（有测试）/ **评测准备度**（门禁配置好）/ **运行时质量**（真实跑过）/ **发布批准**（用户认可）。文件/用例数量只证明第一种。
