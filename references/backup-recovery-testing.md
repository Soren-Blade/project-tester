# 备份与恢复可验证性（R-14）

> **一句话**：没演练过的备份，不叫备份，叫「希望」。
> 备份任务显示 Success，只证明「写文件这个动作没报错」；证明不了文件可读、可解、可恢复到业务可用、且数据没丢。
>
> 适用：有数据库/对象存储/文件上传、有备份策略、宣称 RPO/RTO、需要通过等保/审计/客户尽调、有多租户或 PITR 的项目。
> 配套：`assets/restore-drill-template.md`、`scripts/restore-audit.py`。
> 相关规则：**R-14**；与 R-6（删除权与保留期）、R-9（证据链）、R-13（时间点口径）交叉。

## 0. 什么时候读，什么时候不适用

| 触发信号 | 必做 |
|---|---|
| 有 `backup`、`dump`、`snapshot`、`pg_dump`、`mysqldump`、`wal`、`PITR`、`RPO`、`RTO` | 读全文；至少做一次最小恢复演练 |
| 用户数据/订单/账务/审计日志 | 读全文；必须验证行数/校验和/外键/序列 |
| 多租户 SaaS | 加读 §5（隔离与选择性恢复） |
| 有加密字段/密钥管理 | 加读 §6（恢复后能否解密） |
| 纯无状态服务、无持久化数据 | 写「不适用：无持久化数据」，**不得**写「备份可靠」 |
| 只有云厂商「备份成功」截图 | 不等于可恢复；必须实际 restore 一次到隔离环境 |

## 1. 先把目标写成可测的数字

| 概念 | 可测定义 | 测法 |
|---|---|---|
| RPO（恢复点目标） | 最多可接受丢失多长时间的数据 | 在备份窗口内插入带时间戳的哨兵记录，恢复后看最后一条是哪个时刻；`实际丢失 = 灾难时刻 - 最后可恢复记录时刻` |
| RTO（恢复时间目标） | 从宣布灾难到业务可用的最长时间 | 演练计时：开始 → 数据可读 → 应用健康检查通过 → 冒烟用例通过；分别记录三段耗时 |
| 保留期 | 备份保留多久、多久可删 | 检查保留策略与最近一次可恢复点；保留期 < 最长恢复需求即缺陷 |
| 3-2-1 | 3 份副本、2 种介质、1 份异地/离线 | 核对实际存储位置与账号权限；同账号同区域不算异地 |
| 不可变/WORM | 备份在保留期内不可改删 | 用有写权限的账号尝试删一份旧备份，应被拒绝；勒索软件场景必测 |

> 判据：RPO/RTO 必须是**声明值 + 实测值**两列；只有声明值写「未验证」，只有实测值写「无承诺」。RPO/RTO 的权威口径是业务影响分析（BIA）里由业务方定量的可接受中断/丢失目标（NIST SP 800-34 Rev.1 的定义方式），不是运维拍脑袋填的数字。

## 2. 恢复演练（drill）标准流程

1. **选点**：最近一次成功备份 + 一个历史时间点（验证保留期）+ 一个「刚写入哨兵后」的时间点（验证 RPO 边界）。
2. **隔离**：恢复到独立网络/独立实例/独立账号，禁止覆盖生产；恢复环境与生产同版本镜像。
3. **恢复**：按 runbook 执行，**只允许照文档操作**，不允许「我知道怎么弄」的即兴命令——runbook 缺步骤就是缺陷。
4. **校验不变量**（§3），全部通过才算数据可用。
5. **业务冒烟**：登录、列表、下单/写入、按时间查询、附件下载各一条。
6. **计时**：记录 RTO 三段；记录恢复点与预期 RPO 的差。
7. **清理**：销毁隔离环境与临时凭据；确认没有把生产密钥复制到测试环境。
8. **回写**：`assets/restore-drill-template.md` 落表，缺陷进缺陷表，runbook 就地修订。

> 最小可行演练（时间不够时）：单表恢复 + 行数 + 校验和 + 一条业务查询 + 计时。**不得**因为时间不够就跳过演练并在报告里写「备份正常」。

## 3. 必须校验的不变量

| 类别 | 不变量 | 失败含义 |
|---|---|---|
| 完整性 | 文件数/表数一致；sha256 一致；字节数一致 | 备份截断/损坏/部分写入 |
| 数量 | 每表行数一致；`max(id)` 一致 | 丢行、重复、事务未提交 |
| 序列 | 自增序列/sequence 当前值 ≥ 恢复后 `max(id)` | 恢复后插入主键冲突 |
| 关系 | 外键无孤儿；父子表计数一致 | 部分表恢复导致关系断裂 |
| 大对象 | 附件/图片/文档可下载且 hash 一致 | blob 未备份或存储桶未同步 |
| 配置 | 连接串/队列/密钥引用可用；不是旧环境的硬编码 | 恢复后应用起不来或连错库 |
| 版本 | 应用版本、schema 版本、迁移版本一致 | 代码与库不匹配 |
| 加密 | 加密列可解密；KMS key 仍存在且有权 | 恢复后数据是乱码 |
| 时间 | 恢复时刻晚于备份生成时刻；数据时间戳未被恢复动作改写 | 陈旧恢复/时间口径错乱 |

工具：`python scripts/restore-audit.py compare --source <备份清单> --restored <恢复清单> --fail-on-gap`。

清单最小 schema（两份清单都要，时间必须带偏移）：

```json
{
  "generated_at": "2026-11-14T02:00:00Z",
  "restored_at": "2026-11-14T10:10:00+08:00",
  "app_version": "1.4.2",
  "schema_version": "2026_11_01",
  "files": [{"path": "uploads/a.png", "sha256": "<64hex>", "bytes": 1024}],
  "tables": [{"name": "orders", "rows": 1200, "max_id": 1200}]
}
```

工具输出编号：RST-01 源时间缺失/naive、RST-02 恢复时间缺失/naive、RST-03 恢复早于备份（陈旧）、RST-04 文件缺失、RST-05 多出文件、RST-06 字节数不符、RST-07 hash 缺失/不符、RST-08 表缺失/多表/行数不符、RST-09 序列不符、RST-10 版本不符、RST-11 清单非法。缺 `files`/`tables` 数组时只给 warning「附件完整性未验证 / 行数序列未验证」，**这是盲区，不是通过**。

### 3.1 完整性校验必须「真读数据」

只验证 manifest/文件存在/结构，不算通过——下面这些命令的语义差异必须写进证据：

| 对象 | 弱校验（只查结构） | 强校验（真读内容） |
|---|---|---|
| PostgreSQL 基础备份 | `pg_verifybackup` 的 manifest/文件集合/大小阶段 | 仍要走 checksum 阶段，并按官方文档自己的提醒**做 test restore**（`pg_verifybackup` 通过 ≠ 可恢复） |
| restic | `restic check`（默认只查结构/索引） | `restic check --read-data`，或 `--read-data-subset=1/5` / `2.5%` / `50M` 分片 |
| Borg | `borg check`（仓库 size + CRC32） | `borg check --verify-data`（读全量、解密解压、密码学校验；与 `--repository-only` 冲突） |
| SQLite | 文件存在/大小 | `PRAGMA integrity_check`（期望单行 `ok`）+ `PRAGMA foreign_key_check` |
| 备份文件被篡改（勒索） | 默认 check 可能放过 | 替换一个 pack/segment 后，`--read-data` / `--verify-data` 必须报错 |

> 判据：证据里必须出现「读内容」那一列的命令与输出原文（如 `no errors were found` / `ok`）；只贴「备份成功」或结构检查通过，R-14 不得 PASS。

## 4. 时间点恢复（PITR）专项

- **目标时刻**：选在事务边界（commit 前后）各测一次；恢复后检查该事务是「全有」或「全无」，不得半提交。
- **边界记录**：在目标时刻前后各写一条哨兵，恢复后只应看到前者；后者出现 = 丢数据窗口判断错。
- **WAL/binlog 连续性**：检查归档是否连续；有缺口时最近可恢复点要重新计算，不得沿用旧 RPO 宣传。
- **时钟口径**：备份时间、WAL 时间、应用时间是否同一时钟源；有 skew 时「恢复到 10:00」可能差几分钟。
- **删除权盲区**：用户已删除的数据会随备份复活——恢复后必须重放删除（tombstone/删除日志），使 PII 不「复活」；若技术做不到，必须有书面保留期 + 到期销毁证据（GDPR Art.17 要求「without undue delay」），「备份里就是删不掉」不是可接受答案。这是 R-6 交叉项，必须写结论。
- **恢复后回放**：binlog 重放是否幂等；重复消费/重复扣款如何避免。

## 5. 多租户与选择性恢复

- 单租户恢复时，其他租户数据**不得**出现在恢复环境；用两个租户的哨兵记录验证。
- 共享表（用户表、配置表）按租户过滤恢复时，外键与唯一约束是否仍成立。
- 平台管理员视角能看到哪些租户、恢复后权限是否仍正确。
- 恢复环境的访问控制：临时实例不得对公网开放，临时凭据演练后吊销。

## 6. 密钥、配置与版本

- 备份中的加密字段：恢复后能否用**当前** KMS 密钥解密；密钥轮换后旧备份是否仍可解（密钥版本保留策略）。
- 密钥本身不进备份明文；但「密钥丢失 = 备份全废」，必须确认密钥有独立备份/多区域副本。
- 配置漂移：恢复后应用连的是旧库地址/旧队列；检查环境变量与配置中心。
- 版本兼容：新代码 + 旧库（恢复点旧）能否启动；迁移是否可重入；必要时先跑迁移再验数据。
- 依赖外部服务（对象存储、搜索索引）时，恢复数据库不等于恢复全链路；分别验证。

## 7. 常见陷阱（每条都能变成负向用例）

| 陷阱 | 负向用例 | 期望 |
|---|---|---|
| 备份文件 0 字节/只有头 | 故意放一个空 dump 进恢复流程 | 演练失败并告警，不得显示成功 |
| 备份成功但未包含新表 | 新建表后立即备份再恢复 | 清单里出现该表；缺失即 FAIL |
| 保留期把唯一可用备份删了 | 按策略跑一次清理 | 至少保留满足 RPO 的一份；删除前有保护 |
| 只备份主库不备份序列/扩展 | 恢复后插入新行 | 主键不冲突 |
| 快照 crash-consistent 当成 app-consistent | 备份时有未提交事务 | 恢复后无半写数据；否则记录风险 |
| 恢复到不同区域后 DNS/连接串错 | 按 runbook 切换 | 冒烟通过；文档含切换步骤 |
| 演练用管理员手工命令，runbook 没更新 | 让未参与的人照 runbook 做 | 能独立完成；否则 runbook 缺陷 |
| 备份未加密/权限过宽 | 用普通账号列备份桶 | 拒绝访问；否则 S1 |
| 恢复到非空库静默合并 | 目标库预置一条脏记录后恢复 | 脏记录消失，或恢复显式失败；不得「部分表覆盖、部分保留」 |
| 逻辑恢复不带 sequence 当前值 | 恢复后立刻插入一条新记录 | `last_value >= max(id)` 且插入成功；撞主键即恢复不完整 |
| 删掉中间增量仍报成功 | 隔离一个中间增量再恢复 | 失败并报「缺少某增量」；不得降级到旧点还报成功 |
| 漏 schema/视图/函数/extension/角色/目录 | 恢复前后各导一份对象清单做 diff | diff 为空；非空逐项列出缺什么 |
| 备份密钥与备份放同一台机器 | 干净机器上仅凭文档恢复 | 能解密；若需要「某个人记得的密码」即判失败 |
| 恢复环境默认时区隐式参与 | 在 UTC 与 Asia/Shanghai 两个恢复实例做按日聚合 | 按 UTC 聚合一致；按本地日差异被显式定义，不靠默认值 |

## 8. R-14 证据要求

声称「有备份 / 可恢复 / 满足 RPO/RTO」时至少附：

1. 备份策略原文（频率、保留、位置、加密）+ 最近一次备份的清单/大小/时间；
2. 一次**实际恢复**的记录：恢复点、隔离环境、耗时三段、校验和/行数/序列结果；
3. `restore-audit.py` 输出（或等价的人工对照表），缺口与 warning 都列出；并附**强校验**命令输出（`--read-data` / `--verify-data` / `pg_verifybackup` checksum 阶段），只贴结构检查不算；
4. RPO/RTO 声明值与实测值对照；
5. 删除权/多租户/密钥三类交叉项的结论（适用时）；
6. 演练后修订的 runbook 版本或 diff。

只有「备份任务成功」截图：判「未验证恢复」，R-14 不得写 PASS；缺实际恢复：不得写「可恢复」。

## 9. 常见误判与禁止写法

- 「云厂商说 99.999999999% 持久性」——那是存储持久性，不是你的可恢复性。
- 「每天自动备份，日志显示成功」——只证明任务跑了。
- 「有快照」——快照可能与应用不一致、可能在同账号被删。
- 「RPO 15 分钟」——没测过最后可恢复点，就只是愿望。
- 禁止写：「备份正常」「恢复没问题」「数据不会丢」；改写为「已恢复至 X 时间点，校验 N 项通过，缺失 M 项」。
- 不适用写法：「不适用：无持久化数据，未做恢复演练」。
