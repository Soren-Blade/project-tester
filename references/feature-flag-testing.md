# 特性开关 / 配置 / 灰度正确性（阶段 3/4 · 横向叠加）

> 蒸馏自 Martin Fowler《Feature Toggles》（martinfowler.com/articles/feature-toggles.html，四类 toggle：Release / Experiment / Ops / Permissioning，明确「toggle 应有计划删除日期」）、Open Practice Library《Feature Toggles》（避免长期存活的 toggle、两个状态都要测）、Harness / Rollout.io 的 kill-switch 实践（部署时功能处于休眠态、上线后再翻开关）、SEC 对 Knight Capital 2012 事件的调查报告（遗留的废弃功能开关被重新启用直接导致 45 分钟损失约 4.6 亿美元）、Google SRE 的 progressive / canary rollout 与「actual exposure 须可测量」。来源 URL 与逐条口径见 `CHANGELOG.md` v1.6.0。
> 定位：前面所有手册在回答「**这个功能对不对**」；本手册回答「**在开关/配置/灰度的动态下，它是否仍然正确、是否仍然安全**」。一句话分野：**同一份代码，flag 开与关可能是两个系统；配置漂移与错误的灰度目标，比代码 bug 更难在常规测试里暴露**。

## 0. 适用边界与分工

| 触发 | 叠加本手册 | 不适用 |
|---|---|---|
| 用了特性开关 / kill-switch / 远程配置 / 实验开关 / A-B | 是 | 纯静态、无任何运行时开关或配置化的离线脚本 → 只写「不适用：无开关与配置维度」 |
| 有百分比灰度 / canary / 按用户群放量 | 强制 | 全量一次性发布、无分批 → 只写「不适用：无灰度放量」 |
| 行为由环境变量 / 配置文件 / 远程配置驱动 | 是 | 行为完全硬编码、无外部化配置 → 只写「不适用：无外部化配置」 |
| 想验证「开关关掉系统还安全 / kill-switch 真能止血」 | 强制 | — |
| 只关心单个请求的响应是否正确 | 去 `references/api-testing.md` / `frontend-testing.md` | 开关正确性是在「单请求正确性」之上再加一层动态维度 |
| 想判断该不该发版 | 去 `references/quality-gates.md` §3（R-10 计入 Go/No-Go） | 本手册是发布门禁的输入，不是替代 |

**三条认知打底**：

1. **开关默认态本身就是行为**。一个「默认开」的开关一旦目标系统取不到配置，会回退到「开」并可能把没准备好或危险的路径暴露给所有人——这跟「代码默认走安全路径」是相反假设。2012 年 Knight Capital 正是把一次部署后本应休眠的功能重新点亮，45 分钟损失约 4.6 亿美元。
2. **「功能对」≠「开关隔离对」**。feature 对某用户群可见 ≠ 对其它用户群不可见；灰度 5% 不等于真的只触达 5% 且能随时停。错配目标群体的危害（把内测功能泄露给全员、或把付费功能对免费用户开放）与功能 bug 同级。
3. **配置漂移是静默的**。env / 配置文件 / 远程配置三处不一致时，代码跑的是「你没注意到的那份配置」，且不会有报错。它不同于 R-3 的「制品被改过」，而是「运行时的行为输入被改了」。

> **禁止冒充声明**：任何场景都**不得**把「开态测过」写成「关态也安全」、把「配置三处没比对」写成「开关可控」、把「说 5% 实测」写成「灰度可控」——没有对应证据就降级为「待确认」。

## 1. 为什么这是独立维度（Knight Capital 的教训）

Knight Capital（2012-08-01）的事故要点（SEC 调查报告原文口径）：公司把一个新的部署推到生产，但其中一段**早已废弃、本应休眠的功能**被重新启用（源于未清理的旧功能开关/代码路径），而当时没有对应协调的流量控制，导致系统以错误的方式大量提交订单。后果：约 45 分钟、约 4.6 亿美元损失、几乎导致公司破产。

落到本手册的三条直接推论：

- **废弃开关与「忘了删」的 flag 是高危资产**：任何还活着但不该再触发的开关，必须显式验证「它现在到底会不会被点亮」，不能假设「没人翻它就没事」。
- **开关的默认态与缺失态必须分开测**：取不到配置时回退到哪个态，要写成明确假设并验证，而不是静默回退到「开」。
- **kill-switch 必须经过真关验证**：声称「有问题一键关掉」必须附上「真的把开关关掉后，系统回到安全态」的证据，否则 R-10 判缺口。

> 口径诚实：Knight Capital 案例在公开报道中被广泛归结为「遗留功能开关/代码路径被重新启用 + 缺乏对应控制」，本手册把它作为「开关默认态与废弃开关」的反面教材引用，**不臆造其具体 flag 名称或内部架构**；任何项目引用该案例都应注明「用于说明开关默认态风险，非对其内部实现下结论」。

## 2. 四类必测面（缺一面即 R-10 证据不足）

### 2.1 默认态 / 缺失态安全（默认回到安全路径）

| 测试点 | 通过判据 | 常见失败 |
|---|---|---|
| 开关关闭时功能不可见 / 走旧路径 | 关闭态下新功能入口、API、副作用全部不可达 | 关闭后仍可访问新端点、仍产生新副作用 |
| 开关默认值是「安全态」而非「危险态」 | 配置缺失 / 解析失败时回退到关闭 / 已知安全默认值，而非「开」 | 配置中心宕机 → 全体用户掉进新危险路径 |
| 废弃 / 应休眠的开关确实不会被点亮 | 显式验证该 flag 当前在任何 cohort 都解析为 off（或已被代码移除） | 「以为没人用」的 flag 在灰度里被重新命中 |

### 2.2 目标群体隔离（对的人看得到，错的人看不到）

| 测试点 | 通过判据 | 常见失败 |
|---|---|---|
| 目标群体（按 user/tenant/region/account 属性）看到预期变体 | 目标用户命中变体 A，非目标用户命中变体 B / 旧路径 | 非目标用户也能看到新功能（泄露） |
| 非目标群体看不到新功能 | 同上反向验证 | 免费用户看到付费功能、内测功能泄露给全员 |
| 边界与否定用例 | 属性缺失 / 多值 / 命中多个 segment 时的明确裁决 | 「既是内测又是免费」被错误地放行 |

### 2.3 配置漂移（env / 文件 / 远程配置三处一致）

| 测试点 | 通过判据 | 常见失败 |
|---|---|---|
| 三处配置源一致 | env / 配置文件 / 远程配置对同一 key 的解析结果一致，或明确声明优先级 | 远程配置覆盖了本地，行为与你以为的不一样且无报错 |
| 配置项有 schema / 取值范围校验 | 非法值被拒绝并回退，而非被静默采纳 | 把 `rollout_percent: 500` 当成「全开」或「0」 |
| 配置变更可审计、可回滚 | 改了哪个 key、由谁、何时、回滚命令明确 | 配置漂移无法定位是谁、哪次改的 |

### 2.4 kill-switch 与灰度止血（能停、能回、能控比例）

| 测试点 | 通过判据 | 常见失败 |
|---|---|---|
| kill-switch 真正关闭功能并回到安全态 | 关闭后新功能入口 / 副作用消失，系统可正常服务旧路径 | 关了开关功能还在、或关了之后整个服务挂掉 |
| 灰度比例真实可控 | 实际曝光比例 ≈ 计划比例（实测采样），且有「一键停」 | 说 5% 实际 50%，或停不下来 |
| 回滚是「关开关」而非「回滚代码」 | 止血动作是被测过的轻量开关，不依赖重新部署 | 出事只能紧急回滚发版，恢复时间长 |

## 3. 测试卡（FF-1 ~ FF-12）

| # | 测试动作 | 通过判据 | 常见失败 |
|---|---|---|---|
| FF-1 | 把开关设为 off，走完核心链路 | 新功能全程不可见、无新副作用 | off 态仍暴露新端点 |
| FF-2 | 模拟配置缺失 / 配置中心不可达 | 回退到声明的默认安全态，不回退到「开」 | 缺省即开，全员掉进新路径 |
| FF-3 | 列出所有还活着但不该触发的废弃开关 | 每个都验证当前解析为 off 或已移除 | 「忘了删」的 flag 在灰度被命中 |
| FF-4 | 目标群体命中变体 A | 目标用户看到 A | 目标用户没看到新功能 |
| FF-5 | 非目标群体命中变体 B / 旧路径 | 非目标用户看不到新功能 | 新功能泄露给非目标人群 |
| FF-6 | 属性缺失 / 多 segment 叠加 | 有确定裁决，不静默放行 | 边界用户被错误放行 |
| FF-7 | 改同一 key 为三处不同值 | 实际生效值与声明优先级一致 | 远程配置悄悄覆盖本地，无提示 |
| FF-8 | 配置值越界（如 rollout=500） | 被拒绝并回退 / 明确报错 | 非法值被静默采纳 |
| FF-9 | 真关 kill-switch | 新功能消失且旧路径正常 | 关了还活着，或关了服务挂 |
| FF-10 | 实测灰度曝光比例 | 实测采样 ≈ 计划比例 | 计划 5% 实际 50% |
| FF-11 | 止血动作可一键停 | 停止灰度无残留副作用 | 只能回滚发版才能停 |
| FF-12 | 开关两个状态都跑了常规测试 | 既有「开」的用例也有「关」的用例，不是只测了开 | 关态路径从没被执行过 |
