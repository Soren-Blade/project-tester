# 数据一致性与迁移测试（阶段 2/3 · 有持久化或多存储的项目）

> 蒸馏自 PostgreSQL 事务隔离官方文档、Jepsen 的「操作历史 + 故障 + 一致性检查」思路、`fullstack-dev` 的迁移/事务/缓存/后台任务规则，以及本技能 `references/api-testing.md` §5「响应 + 副作用双重断言」的延伸。
> 定位：`references/api-testing.md` 只要求「查一下 DB 状态」，本手册回答**查什么、怎么算一致、并发下会不会错**。

## 1. 三类风险，别混成一句"数据对不对"

| 类别 | 问题 | 典型漏报 |
|---|---|---|
| 结构一致 | 迁移后 schema 与代码预期是否吻合 | 只测了新写入，没测存量数据 |
| 内容一致 | 写操作是否真的落库、多副本是否相同 | 只验响应码，缓存/索引/读库没更新 |
| 时序一致 | 并发、乱序、重复投递下状态是否合法 | 单线程全绿，并发下双花/库存为负 |

**总纪律**：每个写操作做**三重断言** —— 响应体 + 权威存储（DB）+ 派生状态（缓存 / 索引 / 事件 / 读副本）。缺一项就写「部分验证」。

## 2. 数据库迁移测试（上线前必做）

| # | 用例 | 通过判据 |
|---|---|---|
| 1 | 从空库跑全量 `up` | 一次成功，无人工干预；耗时记录 |
| 2 | `up → down → up` | 可往返，无残留对象、无数据丢失 |
| 3 | 有存量的库上跑 `up`（用**类生产数据量**的合成数据） | 不锁死全表、不超时、旧行被正确回填 |
| 4 | 迁移失败中途 | 事务性 DDL 回滚，或明确文档化的不可回滚步骤 + 补偿脚本 |
| 5 | 新旧代码并存（滚动发布窗口） | 老版本代码能读写新 schema（expand → migrate → contract） |
| 6 | 迁移幂等 | 重复执行不报错、不重复加列/加索引 |
| 7 | 回填校验 | 新增字段在**所有**历史行上都有值，NULL 数量符合预期 |

```sql
-- 迁移前后各跑一次，作为可粘贴的 checksum 证据
SELECT count(*) AS rows, count(*) FILTER (WHERE new_col IS NULL) AS nulls,
       min(created_at), max(created_at) FROM orders;
-- 结构快照
SELECT column_name, data_type, is_nullable FROM information_schema.columns
WHERE table_name = 'orders' ORDER BY ordinal_position;
```

**证据要求**：把迁移前/后的行数、NULL 数、checksum、耗时写成两列对照；只写"迁移成功"不算通过。

## 3. 事务边界与并发异常（SQL 标准四现象）

隔离级别与异常对照（PostgreSQL 口径，其他库按其文档校准）：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 序列化异常 |
|---|---|---|---|---|
| Read uncommitted（PG 等同 Read committed） | 标准允许 / PG 不发生 | 可能 | 可能 | 可能 |
| **Read committed（PG 默认）** | 禁止 | **可能** | **可能** | **可能** |
| Repeatable read | 禁止 | 禁止 | PG 中不发生 | 可能 |
| Serializable | 禁止 | 禁止 | 禁止 | 禁止（需准备重试） |

**必须测的四条**（并发用后台进程即可，无需框架）：

```bash
# ① 双花 / 超卖：同一账户或同一库存并发扣减 N 次
for i in $(seq 1 10); do
  curl -s -o /dev/null -X POST -H "Content-Type: application/json" \
    -d '{"sku":"p1","qty":1}' http://127.0.0.1:3000/api/deduct &
done; wait
# 判据：最终库存 = 初始值 - 成功次数；绝不为负；无重复扣减
```

| # | 用例 | 期望 |
|---|---|---|
| 1 | 多步写（建单 + 扣库存 + 记账）中途失败 | **全部回滚**，不留半条订单 |
| 2 | 同一事务内连续两次读，中间被另一事务修改 | 明确知道该隔离级别下允许什么；业务若要求一致需升级隔离或加锁 |
| 3 | 并发更新同一行 | 乐观锁/版本号生效，失败方收到明确冲突码而非静默覆盖 |
| 4 | Serializable 下的序列化失败 | 应用有重试，不是直接 500 |
| 5 | 长事务 / 未提交事务 | 不长时间持锁；超时有上限 |

**判据写法**：并发用例报「并发数 / 执行次数 / 成功次数 / 最终状态 / 异常数」，不要只写"没报错"。

## 4. 多存储与缓存一致性

| 场景 | 最小测试动作 | 通过判据 |
|---|---|---|
| Cache-aside | 写后读、写后再读、缓存过期后读 | 写操作后缓存被删/更新；否则读到旧值 = bug |
| TTL | 设短 TTL，等待过期后读 | 所有缓存都有 TTL；**无 TTL 的缓存视为缺陷** |
| 双写 / 回填 | 故意让第二个存储写失败 | 有补偿、对账或幂等重放，不长期不一致 |
| 主从 / 读副本 | 写后立即从读副本读 | 明确告知"读己之写"是否保证；不保证则需路由或等待 |
| 事件 / CDC | 写库后检查消息是否发出、顺序是否正确 | 事件与库状态可对账；乱序/重复不破坏最终状态 |
| 后台任务幂等 | 同一 job 手动执行两次 | 结果一致（不重复扣款/发信）；不能假定"恰好一次" |
| 死信队列 | 让任务连续失败到上限 | 进 DLQ 并告警，不是无限重试或静默丢弃 |

**对账脚本**（零依赖，任何有 SQL 客户端的项目都能跑）：

```bash
# 主从行数对账（替换连接串即可）
a=$(psql "$PRIMARY" -tAc "SELECT count(*) FROM orders");
b=$(psql "$REPLICA" -tAc "SELECT count(*) FROM orders");
[[ "$a" == "$b" ]] && echo "PASS $a" || echo "FAIL primary=$a replica=$b"
```

## 5. 幂等键、去重与状态机

- 幂等键：同一 key 重放返回**同一结果**（不是同一状态码但内容不同）；过期策略与作用域要写清
- 回调/webhook 重复、乱序、延迟到达：状态机合法迁移表之外的操作一律拒绝并有明确错误码（见 `references/api-testing.md` §5）
- 软删除 + 唯一约束：删后重建同名资源不应撞唯一键，也不应双份存在
- 时间边界：跨天/跨月/时区/闰秒类逻辑用注入时钟测，别依赖真实时间

## 6. 零依赖降级与证据

| 条件 | 做法 | 报告里怎么写 |
|---|---|---|
| 有 DB 客户端 | 直接跑 §2/§4 的 SQL 与对账 | 附两条原始输出 |
| 只有 HTTP | 通过 API 读回比对，配合响应体断言 | 「未直接查库，间接验证」 |
| 完全跑不起来 | 静态审读迁移文件、事务注解、缓存失效代码 | 「静态审查，未运行时验证」，标 🔥 |
| 多副本/分布式 | 记录操作起止历史 + 注入故障 + 事后一致性检查（Jepsen 思路） | 写明并发模型与检查的不变量 |

**不变量（invariant）比期望值更好用**：如「总金额守恒」「库存 ≥ 0」「订单数 = 事件数」「分页合并 = 全量集合」——无需预知正确结果就能判错（蜕变关系见 `references/test-design.md`）。

## 8. 反模式

| ❌ | ✅ |
|---|---|
| "接口返回 201"就算写成功 | 三重断言：响应 + DB + 派生状态 |
| 只在空库上测迁移 | 用类生产数据量的合成数据 |
| 只测 `up` 不测 `down` | 往返都要跑，回滚要能演练 |
| 并发用 `sleep` 猜时序 | 用真实并发 + 记录最终状态与不变量 |
| 把缓存当权威状态 | 缓存必须有 TTL 且写后失效 |
| 一致性问题只写"偶现" | 附并发数、次数、最终状态、复现命令 |

> **判定口径**：数据损坏、丢数据、双花/超卖、迁移导致存量数据不可用一律 **S1**（`references/quality-gates.md` §2）；仅有不一致窗口但可自愈且业务可接受，记为 S2 并在报告写明窗口时长与影响面。
