# 自我进化机制（阶段 4 详版 · v1.0）

> 本文件负责**运行时**（用技能测项目时）的进化回路；技能本体如何每日升级、版本与门禁见 **`self-evolution.md`**（元规范）。两者权限不同，不要混淆。

进化 = 每次测试都让下一次更准、更快。载体是三层记忆 + 一个版本日志：

```
第 1 层 项目级   <项目>/.test-memory/lessons.md      本项目的坑与回归关注点
第 2 层 跨项目   <技能>/memory/global-lessons.md      通用规律，开局即读
第 3 层 技能本体 SKILL.md / references / assets      流程与手法（仅每日升级授权时可改）
追溯层         CHANGELOG.md + version                 为什么改、依据什么、怎么验的
```

## 1. 每次运行结束的进化检查（必答四问）

1. **这次踩了什么坑？** 环境问题、工具误用、误报的 bug → 有通用性的写第 2 层，仅本项目相关的写第 1 层
2. **什么手法特别有效？** 比如某类项目先跑某命令省一半时间 → 固化进 `global-lessons.md`，下次直接用
3. **证据够不够？** 失败结论是否都有 MRE + 实际输出？指标是否写清分子/分母？缺证据的标 `BLOCKED`（见 `quality-gates.md` §7）
4. **技能流程本身哪里不够？** 指引缺失/误导、模板字段不够、新项目形态没有路由 → 记入 `global-lessons.md` 的 `[技能改进]` 提案区，并在报告末尾提议；**运行时不自行改动 SKILL.md / references**

> 权限裁决（详见 `self-evolution.md` §1）：**测项目时不自治，升级技能时授权自治**。`[技能改进]` 提案区正是每日升级任务的输入队列。

## 2. 四层能力视角（判断该把经验放哪）

| 层 | 经验类型 | 例子 |
|---|---|---|
| L1 Core | 测试设计、用例、缺陷、报告 | "空输入是最便宜的 bug 探针" |
| L2 Engineering | 工具、自动化、契约、性能、CI | "有 OpenAPI 就先跑 schemathesis" |
| L3 Production | 发布门禁、监控、事故 | "回滚预案没演练过就等于没有" |
| L4 AI Native | AI 辅助生成、AI 系统评测 | "healer 改断言必须人工复核" |

写教训时顺手标层，升级时就能快速判断该 `Enhance` 哪份手册。

## 3. global-lessons.md 格式

与项目级 lessons.md 相同，一行一条：`[标签] 教训 — 应用：怎么用`。

标签建议：环境 / 工具 / 流程 / 手法 / 安全 / 技能改进 / AI。

条目超过 40 行时修剪：连续两次测试都没用上的条目移入文末"归档"区或删除。**教训必须可执行，不写空话**（❌"要认真测试"；✅"Express 项目先测空 body，默认没校验"）。`[技能改进]` 提案被升级吸收后，在 `CHANGELOG.md` 标注"已吸收 / 已驳回 + 理由"。

## 4. 进化如何生效

- 阶段 0 就读 `global-lessons.md` —— 上次的经验本次开局即生效，这是最短的进化回路
- 项目教训随记忆树接力生效
- `[技能改进]` 提案 → 每日升级任务（B 上下文）按 `self-evolution.md` §3 的十步门禁处理 → 改源文件 → 全局同步 → git 提交 → 版本号 +1
- 升级后的新手册通过 `dissect.md` §8 的能力层路由被下次测试自动选中

## 5. 衡量进化（可选，写给用户看）

报告末尾可附一行：`本轮进化：新增教训 N 条（项目 n / 全局 m），技能改进提案 p 条；下次预计省时 X`。让进化可见，才有无限进步的正反馈。

但必须区分四种结论，**不许互相冒充**：静态记录（文件写了）／评测准备度（有自检）／运行时质量（真测过项目）／发布批准（用户认可）。文件数量增加只证明第一种；省时是估计值，不是承诺。
