# 测试设计方法论（阶段 2 详版）

> 蒸馏自经典测试设计（ISTQB 体系）、`fullstack-dev/references/testing-strategy.md`、以及 `naodeng/awesome-qa-skills` 的 Core QA 能力分层。
> 目标：把「功能清单」变成**有限但高杀伤力**的测试点集合，而不是靠"多试几次"碰运气。

## 1. 为什么需要设计：穷举不可能

一个 5 字段表单、每字段 10 个取值 = 10⁵ 组合。设计的本质是**用等价类把无限输入压缩成有限代表**，再用边界与组合把高风险区补回来。

三条铁律：

1. **先分层再取值**：先确定"哪类输入可能走不同代码路径"，再挑代表值
2. **失效优先于覆盖**：优先覆盖"错了代价最大"的路径，而不是"最容易写"的路径
3. **每个测试点必须有预期**：没有明确预期的执行不叫测试，叫"看看会怎样"

## 2. 测试设计九式（按项目形态挑，不必全用）

| # | 手法 | 何时用 | 最小做法 | 典型漏网 bug |
|---|---|---|---|---|
| 1 | 等价类划分 | 任何有输入域的功能 | 有效类 1 个 + 无效类每类 1 个 | 非法类型被静默接受 |
| 2 | 边界值分析 | 数值/长度/日期/分页 | `min-1, min, min+1, max-1, max, max+1` | 差一错误、翻页丢最后一条 |
| 3 | 判定表 | 多条件组合决定动作（折扣、权限、风控） | 条件 × 规则矩阵，合并无关项 | 组合分支漏判 |
| 4 | 状态迁移 | 订单/工单/审批/会话等有状态对象 | 画状态图，测合法迁移 + **非法迁移** | 跳过前置状态直达内部 |
| 5 | 成对组合 (pairwise) | 3~8 个独立参数 | 保证任意两参数每个取值组合至少出现一次 | 参数间隐式耦合 |
| 6 | 错误推测 | 有经验后的补充 | 基于历史 bug 清单反推（本技能 `memory/global-lessons.md`） | 团队反复踩的老坑 |
| 7 | 基于属性的测试 | 纯函数、序列化、数据转换 | 声明不变量，让工具生成上百组输入 | 罕见的输入形状 |
| 8 | 蜕变测试 (metamorphic) | **没有可靠预期输出**时（AI、搜索、推荐、图算法） | 定义变换关系：打乱输入顺序结果应等价；加一个不该影响结果的条件结果不变 | 无法写断言的黑盒 |
| 9 | 探索式会话 | 需求不清、时间盒短 | 45 分钟 charter + 现场记录，产物回填测试矩阵 | 脚本化测试想不到的路径 |

**属性测试不变量示例**：`decode(encode(x)) == x`、排序后长度不变且单调递增、分页合并后与全量集合相同、金额求和与明细求和一致、重复调用结果幂等。

## 3. 六维测试矩阵 v2（阶段 2 的产出格式）

每个功能 × 六个维度，不适用的划掉并写原因，不许留空：

| 维度 | 必问 | 最小测试点 | 参考手册 |
|---|---|---|---|
| 正确性 | 主流程对不对？宣称 vs 实际一致吗？ |  happy path + 文档一致性 | `dissect.md` |
| 边界 | 空/零/最大/超长/特殊字符？ | 边界值三件套 | `personas.md` |
| 异常 | 依赖挂了、超时、脏数据？ | 超时/断连/畸形输入 | `fullstack-integration.md` |
| 安全 | 未授权能访问吗？能改别人数据吗？ | 认证/授权/注入/泄漏 | `security-testing.md` |
| 性能 | 慢不慢？量大时会不会崩？ | p95 + 大数据量 + 并发 | `performance-testing.md` |
| 体验 | 出错看得懂吗？状态全吗？ | 加载/空/错误/成功四态 | `frontend-testing.md` |

## 4. 风险驱动优先级（替代拍脑袋的 P0/P1/P2）

对每个功能算一个简版风险分，降序执行：

```
风险分 = 失效影响(1~3) × 失效概率(1~3) × 暴露面(1~3)
```

| 因子 | 1 | 2 | 3 |
|---|---|---|---|
| 影响 | 体验轻微 | 功能不可用 / 需绕过 | 数据损坏 / 越权 / 资金 / 崩溃 |
| 概率 | 有校验、逻辑简单 | 新代码 / 多分支 / 外部依赖 | 历史上出过 bug / 无校验 |
| 暴露面 | 内部、需特权 | 登录用户可用 | 匿名公网可达 |

- ≥ 18 → **P0 全测**（六个维度全覆盖 + 回归）
- 9~17 → **P1 核心路径**（正确性 + 边界 + 安全）
- ≤ 8 → **P2 抽样**（正确性冒烟，视时间）

写进测试计划时保留分数，下次接力能直接看出为什么当初这么排。

## 5. 覆盖准则与退出标准（什么时候可以停）

不同项目用不同口径，**先声明口径再报数字**，禁止只报一个"覆盖率 80%"：

| 准则 | 含义 | 适用 |
|---|---|---|
| 功能点覆盖 | 测试矩阵中已执行 / 总测试点 | 所有项目（本技能默认口径） |
| 等价类覆盖 | 已覆盖等价类 / 总等价类 | 有明确输入域 |
| 分支覆盖 | 代码分支命中率 | 单测（`--coverage`） |
| 变异得分 | 被杀死的变异体 / 总变异体 | 想验证"测试有没有杀伤力"时 |
| 接口覆盖 | 已实调端点 × 动词 / 总端点 × 动词 | API 项目 |
| 风险覆盖 | 已测 P0 风险分之和 / 全部 P0 风险分之和 | 时间受限需向用户交代时 |

**退出标准（默认，可在计划里改）**：P0 功能点覆盖 100% 且无未闭环严重 bug；P1 ≥ 80%；所有失败结论都带证据；`tree.md` 已更新。达不到就明写"未达标 + 原因 + 剩余风险"，不许含糊成"基本测完了"。

> 覆盖率只说明"代码被执行过"，不说明"断言有效"。高覆盖 + 低变异得分 = 一堆假测试。见 `quality-gates.md`。

## 6. 测试点写法（拒绝不可执行的需求）

```
❌ 测试登录功能是否正常
❌ 检查安全性
✅ 用不存在的用户名 + 任意密码 POST /api/login → 期望 401 且响应不含 "user not found" 之外的账号枚举线索
✅ 同一请求连续发 2 次 → 期望仅创建 1 条记录（幂等）
```

一条合格测试点 = **输入 + 动作 + 可观测预期**，三者缺一不可。

## 7. 与记忆树的接口

- 阶段 2 产出的测试矩阵写入当次 `runs/` 记录的"测试点结论"表
- `tree.md` 的模块树叶子 = 测试点，状态随结论更新
- 被判定为"通用手法"的设计经验 → `memory/global-lessons.md`，标签 `[手法]`
- 被判定为"本项目特有"的 → 项目 `.test-memory/lessons.md`

## 8. 反模式

| ❌ | ✅ |
|---|---|
| 只测 happy path | 每个功能至少 1 无效 + 1 边界 |
| 用例依赖执行顺序 | 每条自带 setup/teardown |
| 硬编码测试数据 | 工厂 + 覆盖参数（`faker` / factory_boy） |
| 用"跑了一遍没报错"当通过 | 有明确断言与预期值 |
| 测实现细节 | 测行为：输入 → 可观测输出 |
| 把重试当修复 | 见 `quality-gates.md` 的 flaky 治理 |
